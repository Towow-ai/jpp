## 一、这份标准评什么，怎么用

Nature 2026-09-23 的要求分两层。第一层是设计：它回答了我们所有的问题，照这个设计走就能解决那些问题。第二层是架构：在第一层成立的前提下，梳理出最干净的结构，使未来改动的成本最低。Nature 同时指出设计与架构是绑在一起的，评价架构应有详细的标准，照标准做，做不好再修。

本文只服务第二层，但每个维度都写明它服务第一层的哪一条目标。理由是：一个在通用编译器工程意义上干净、却让八条缝仍由使用者承担的架构，对本项目没有价值。所以每一维都挂到 `00` 系列的四类锚点之一：八条缝、`00-目标与动机` §6 的三条验收、`00-定位与方法论` §二的三个预言、§八的跑偏清单。挂不上的维度不进本标准。

打分规则有三条。其一，每一维 0–3 四档，每档对应一个可观测事实（能 grep、能跑、能数），不使用「较好」「基本」这类需要评审者主观判断的词。其二，凡涉及「改动要碰多少地方」的维度，统一对着 §三 的标准变化场景集计数，使扩展性、改动成本、模块边界、规模经济四维的数字可以互相比较；这是 ATAM 质量属性场景法的做法（Kazman、Klein、Clements，SEI），这里把场景固定下来，不每次评审现编。其三，评审报告给出各维剖面，不求加权总分；另设门槛维度（§六），门槛维度低于 2 分时架构方案不得定稿。

## 二、与全项目共识的对照，以及冲突标注

本节列出任务说明与共识不一致之处，以及本文的处理。

1. **「判断器为底层效应」与「各效应同级」冲突。** 派发本任务的说明把 J++ 描述为「判断器为底层效应」的语言。`00-定位与方法论` §二 与术语表的表述是：`judge`、`gen`、`do`、`ask` 与宿主变换 `transform` 同级，各带能力画像，差别只在画像字段；`judge` 的特殊之处只在它是唯一产出读数、必须过桥的效应。本文按共识处理：扩展性维度（D5）奖励「所有效应经同一个带画像的机制注册」，不奖励为 `judge` 单开的特权路径；过桥（`cut`）作为读数专属的不变量放在 D4。
2. **术语。** 本文用「能力画像」，不用「档案」；`12` 与代码里的 `Profile`、「档案」指同一物。「题类」指题的分类（属性、关系、子集……），「题式」指带参数槽的题模板。缝的条数是八条（`16` §4 之后），不是 `00-目标与动机` §3 表里的六条。
3. **任务说明中的「料库、题库、缓存」等存储对象**在 `12` §5 属于「库」层，不是语言内核。本文 D11 评的是内核为这些存储提供的持久化接口与一致性，不评库的内容。
4. **规模经济用「架构文档行数与代码行数之比」**：这个比值没有单调的好坏方向，可以靠加长或删减文档刷数。本文 D18 保留它作为报告项，但打分改用两个有方向的量（见 D18）。

## 三、标准变化场景集

以下十个标准变化场景是评审时统一使用的改动基准。评审者对每个场景写出最小改动集，数四个量：触及的 crate 数、触及的源文件数、需要新增或修改的 `match` 分支数、需要同步修改的既有测试文件数。另记第五个量：执行该场景前必须读完的文档与代码行数（D18 用）。

| 编号 | 场景 | 对应的扩展点 | 为什么选它 |
|---|---|---|---|
| S1 | 接入第二个判断器（新客户端 + 新能力画像），`.jpp` 程序不改 | 后端 | 预言 1、验收 3「换接口」 |
| S2 | 新增一种效应（例如「检索」，有成本、时延、并发画像，不产出读数） | 效应 | 各效应同级是否落到结构上 |
| S3 | 新增一个语言构造（例如 `pair` 配对算子，或自指） | 构造 | `16` §一 五个算子尚未到位，这是近期必然发生的改动 |
| S4 | 新增一条检查规则 J-19（静态面 + 运行面） | 规则 | 检查规则是 J++ 语言级保证的载体 |
| S5 | 新增一个 pass（例如 `fission`） | pass | `12` §4 九个 pass 中四个未落地 |
| S6 | 账本键加一个字段（例如题式版本） | 存储格式 | 键的等价性决定缓存与重放 |
| S7 | 更换校准方法（例如校准键主键改为题式，`17` 阶段 3） | 校准 | 已排进计划的真实改动 |
| S8 | 新增一类持久存储（例如题库，`12` §5 B21） | 存储 | 阶段 4 独立交付物 |
| S9 | 把内核嵌入另一个宿主（例如被 Python 构建器以库方式调用） | 宿主接口 | 适用场景覆盖 |
| S10 | 改一个能力画像字段的语义（例如 `concurrency` 改为按状态大小给出） | 画像 | 跑偏清单第 3 条的反面检验 |

**计数示范（HEAD 947d4b8，只示范取数方法，不是评分）。** `jpp-core/src/effects.rs` 的 `Client` trait 把 `judge`、`generate`、`ask` 三个效应放在同一个 trait 里。`git grep 'impl Client for'` 得到 45 处实现，分布在 33 个文件，其中 4 处是生产实现（`FixedClient`、`NoCallClient`、`JevClient`、CLI 的 `ReplayClient`），其余是测试桩。若 S2 以「给 `Client` 加一个无默认实现的方法」完成，最小改动集至少触及 33 个文件。若改为带默认实现的方法，改动只触及 1 个文件，但漏写实现的客户端要到运行期才暴露，按 D6.2 这是更差的结果。这两个数字说明的是 S2 当前的改动成本，是否可接受由 D5、D6 的刻度决定。

## 五、逐维细则

每维给出：定义；为什么对 J++ 重要；判据（编号，可判真假或可度量）；0–3 刻度；参考出处，每条出处附一行「条件变化」，按 `00-定位与方法论` §四 的借用登记要求写明原场景与本项目的差别。

### D1 分层与阶段分离

**定义。** 实现被划分为有明确输入输出类型的阶段（词法、语法、降级、静态检查、计划、执行、报告），后一阶段只消费前一阶段的产物。

**为什么重要。** 八条缝要求整程序分析（`00-定位与方法论` §三）。批调度与预算需要在执行前看到整个程序或至少整个刷新区间；如果解析、检查、调度、执行交织在一个遍历里，整程序视图就只能靠在执行中途回看来模拟，缝就会退回局部决定。

**判据。**
- D1.1 能否列出阶段清单，每个阶段有一个入口函数和一个输出类型？（是/否）
- D1.2 检查阶段是否只读 IR 或 AST，不读源文本、不调用客户端？（grep 检查模块对 `Client`、文件 IO 的引用数，目标 0）
- D1.3 执行阶段是否不再做语法层判断（例如按语法形状识别可批处理的题）？`16` §七 原文：「顺带那个十四倍会从『靠 pass 认语法』变成『结构上不可能写错』」，说明当前属于此类问题。计数：执行模块中按 AST 语法形状分支以决定调度的位置数。
- D1.4 前端 crate 是否不含执行代码？（`jpp-frontend/src/lower.rs` 首行声明「No execution lives here」，需以依赖图核实）

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无法列出阶段清单；检查与执行在同一遍历中完成 |
| 1 | 阶段清单可列出，但 D1.2 或 D1.4 至少一项不成立 |
| 2 | D1.1、D1.2、D1.4 成立；D1.3 计数大于 0 |
| 3 | 四项全部成立，且每个阶段有独立测试入口 |

**出处。** rustc 开发指南 Overview（token → AST → HIR → THIR → MIR → LLVM IR，各 IR 为不同分析服务）。Nystrom《Crafting Interpreters》第 2 章 A Map of the Territory（扫描、解析、静态分析、IR、优化、代码生成、运行时）。条件变化：这些阶段划分服务于「源程序 → 机器码」；J++ 的执行产物是对外部组件的调用与账本，计划阶段（批调度、预算）比代码生成更关键。

### D2 IR 设计

**定义。** 前端语法树与执行器之间，存在一个或多个中间表示，承载 pass 的输入输出，并有可执行的良构检查。

**为什么重要，以及为什么是有条件的要求。** Lua 5.0 的编译器没有 IR，边解析边生成虚拟机指令，这对 Lua「简单、可嵌入、低嵌入成本」的目标是合适的（Ierusalimschy 等 2005）。所以「有 IR」本身不是优点。J++ 需要 IR 的理由来自自身：`12` §4 规定九个 pass 各有开关以便消融，刷新点要把已登记的效应按依赖排成层；这些操作需要一个能被检查、打印、比较的表示。若 pass 直接写在解释器的求值循环里，关掉某个 pass 的效果就只能靠运行时标志位分散判断，消融的对照臂不干净。

**判据。**
- D2.1 前端 AST 与执行器之间是否有 IR 类型，与语法 AST 分开？（是/否）
- D2.2 IR 是否能表达六种形式（`state`、`judge`、`cut`、`gen`、`do`、`ask`）加 `transform`、`fit`，且每种形式只有一个变体？
- D2.3 是否有 IR 良构检查器，可在任一 pass 前后运行？（nanopass 的「输出语言项良构」检查）
- D2.4 是否能在任一 pass 之后打印 IR（文本形式，可 diff）？
- D2.5 IR 是否携带账本键所需的全部字段，使键可以从 IR 节点单独算出，不依赖执行中途状态？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | D2.1 不成立：pass 逻辑写在求值循环里 |
| 1 | 有 IR 类型，但 D2.2 或 D2.5 不成立 |
| 2 | D2.1、D2.2、D2.5 成立；缺良构检查或缺打印 |
| 3 | 五项全部成立 |

**出处。** Keep & Dybvig，A Nanopass Framework for Commercial Compiler Development，ICFP 2013：Chez Scheme 原编译器由 10 个多用途 pass 组成，新编译器把其中 5 个替换为 50 多个 nanopass，整体约 50 个单任务 pass、约 35 种形式定义的中间语言，编译时间保持在原编译器两倍以内；形式定义的中间语言使框架能检查输出项良构。rustc MIR（为借用检查与数据流分析而设的控制流图）。Ierusalimschy、de Figueiredo、Celes，The Implementation of Lua 5.0，JUCS 2005：「The Lua compiler uses no intermediate representation」。Soufflé：Datalog 程序先降级为关系代数机（RAM），再解释执行或合成 C++，逻辑程序与执行方式分开。条件变化：nanopass 与 MIR 的 pass 是纯变换；J++ 的 pass 决定对外部组件的调用次数与花费，pass 正确性除了「语义等价」还要求「花费不超预算、推测不执行 `do`」，良构检查之外还需要 D10 的等价对照。

### D3 模块边界与依赖方向

**定义。** 模块按「隐藏哪一项会变的设计决定」划分，依赖方向从易变指向稳定，依赖图无环。

**为什么重要。** J++ 中最常变的决定是：判断器是谁（画像）、校准方法、题库内容、宿主形式。最稳定的是内核：两类型、桥、三值出口、账本、未决必须消费。如果内核依赖某个判断器客户端的具体实现，换判断器就要改内核，预言 1 与验收 3 失效。

**判据。**
- D3.1 crate 与模块依赖图是否无环？（`cargo` 层面无环由工具保证；模块层用 `use` 图检查）
- D3.2 为每个模块写一句「它隐藏的设计决定」，写不出的模块数。
- D3.3 内核（类型、桥、出口、账本、检查）是否不依赖任何具体客户端实现、文件格式或 CLI？计数：内核模块对 `JevClient`、HTTP、文件路径的直接引用数。
- D3.4 单文件行数上限：超过 1500 行且包含两个以上 D3.2 意义下设计决定的文件数。
- D3.5 公共 API 与内部项是否分开（Rust `pub(crate)`、Go `internal` 的作用）？计数：被 crate 外使用的 `pub` 项占全部 `pub` 项的比例。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 存在依赖环，或内核直接依赖具体客户端 |
| 1 | 无环；D3.3 计数大于 0 |
| 2 | 无环，D3.3 为 0；D3.2 或 D3.4 计数大于 0 |
| 3 | 以上全部为 0，且 D3.5 有明确的公共/内部划分 |

**出处。** Parnas，On the Criteria To Be Used in Decomposing Systems into Modules，CACM 1972：以「难的或可能变的设计决定」为模块划分依据，每个模块向其他模块隐藏一项决定。Go 模块布局文档：`internal` 目录使内部包「free to refactor」。ISO/IEC 25010 可维护性子特性「模块性」：对一个组件的改动对其他组件影响最小。条件变化：Parnas 的「会变的决定」在 J++ 中有一个特殊来源，即判断器能力随时间变化（`00-定位与方法论` §二），这使「画像」必须是一个独立模块的隐藏决定，而不是散布在各处的常量。

### D4 不变量强制点

**定义。** 每条语言级不变量（J-01 至 J-18、类不变量 I、`cut` 是读数唯一出口、未决必须消费）在实现中有登记的强制点：一个静态检查位置，可选一个运行期兜底位置，二者在登记表中写明分工。

**为什么重要。** J++ 的保证不是性能指标，是语义承诺：读数不喂回判断器、阈值不手写、未决必须消费。一条不变量若在三处各守一部分，改其中一处时另两处不会报错，保证会悄悄失效。`00-目标与动机` §4 指出 J-05 是深度的使能机制，它的强制点是否唯一直接决定验收 2。

**判据。**
- D4.1 是否存在不变量登记表：不变量 → 静态强制点（文件:函数）→ 运行期兜底点 → 测试？
- D4.2 每条不变量的强制点数：静态面不超过 1 处，运行面不超过 1 处。超出的不变量条数。
- D4.3 每条不变量是否有「绕过测试」：构造一个违反它的程序，断言被拒？缺绕过测试的条数。
- D4.4 强制点是否位于所有路径必经之处（例如所有效应结果都经同一个构造函数进入值域）？计数：能构造出目标类型值却不经强制点的构造路径数。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无登记表；至少一条不变量找不到强制点 |
| 1 | 有登记表；D4.2 超出条数大于 0 |
| 2 | D4.2 为 0；D4.3 或 D4.4 计数大于 0 |
| 3 | 四项全部满足：每条恰有登记强制点，绕过测试全部失败于预期位置 |

**取数示范（HEAD 947d4b8）。** `git grep -c` 统计条文引用：J-05 在 `check.rs` 14 处、`interp.rs` 18 处、另三个文件各 1–2 处；J-03 分布在 7 个文件。引用数不等于强制点数，登记表需要逐处人工分类（强制、注释、报文）。这一统计说明登记表是必需的。

**出处。** Wasm 规范 1.1 引言：代码先验证再执行（validation before execution），验证器是单一入口。Rust 类型系统的「解析，不要校验」做法（构造函数是唯一入口，值一旦构造即满足不变量）。条件变化：Wasm 的不变量全部可静态判定；J++ 有一部分不变量依赖运行期读数（例如未决是否真的被消费取决于走了哪条分支），所以允许「一处静态 + 一处运行期」的双点，但双点必须登记分工。

### D5 扩展性（后端、效应、构造、规则、pass）

**定义。** 对 §三 的 S1–S5，最小改动集的大小。

**为什么重要。** 预言 1「判断器能力越强，程序效果越强，程序不改」依赖 S1 的成本；共识「各效应同级」依赖 S2 的成本；`17` 阶段 3 的五个算子依赖 S3；检查规则与 pass 的增补是常态。

**判据。** 对 S1–S5 各数四个量（crate、文件、`match` 分支、既有测试文件）。额外判据：
- D5.1 S1 是否只新增文件，不修改内核文件？
- D5.2 S2 新增效应时，是否经与 `judge`、`gen`、`do`、`ask` 相同的注册机制（带能力画像），而不是在客户端 trait 上加方法？
- D5.3 S4 新增规则时，是否只需新增一个规则单元并在一处注册？（go/analysis 的 Analyzer 模式）
- D5.4 S5 新增 pass 时，是否只需实现 pass 接口并加入 pass 列表，开关、打印、消融自动获得？

**刻度（按场景分别打，维度分取五个场景的最低分）。**
| 分 | 可观测事实 |
|---|---|
| 0 | 该场景需修改 5 个以上既有源文件，或需修改 10 个以上既有测试文件 |
| 1 | 修改 3–4 个既有源文件 |
| 2 | 修改 1–2 个既有源文件（通常为一处注册表） |
| 3 | 只新增文件，外加一行注册；既有测试文件不改 |

**出处。** LLVM 新 pass 管理器文档：pass 流水线有文本描述（`module(cgscc(function(loop())))`），可经回调插入单个 pass，分析与变换分开并由 `PreservedAnalyses` 声明失效范围。golang.org/x/tools/go/analysis：Analyzer 为单元，`Requires` 声明依赖且必须无环，驱动程序与分析器分离，「checkers from a variety of sources can be easily selected, incorporated, and reused」。Graefe，The Cascades Framework for Query Optimization，IEEE Data Eng. Bull. 1995：优化以规则集扩展。Sivaramakrishnan 等，Retrofitting Effect Handlers onto OCaml，PLDI 2021：新增效应机制时以「不用效应的程序平均开销 1%」为约束。条件变化：LLVM 与 go/analysis 的扩展单元彼此独立；J++ 的新效应需要同时进入计划（成本估算）、调度（并发画像）、账本（键）、taint（输出标签）四处，所以 S2 的「只新增文件」要求效应描述本身携带这四类信息。

### D6 改动成本

**定义。** 对 §三 的 S6–S10，最小改动集的大小，以及遗漏改动时是否有测试或编译错误发现它。

**为什么重要。** Nature 要求「未来你要改动啊什么的，它的成本最低」。`17` 已排定的改动（校准键改为题式、题库、账本键加字段）都是 S6–S8 这类跨切面的改动。

**判据。**
- D6.1 S6–S10 各自的四个计数。
- D6.2 遗漏检测：在最小改动集中故意漏改一处，是编译错误、测试失败、还是静默通过？静默通过的场景数。
- D6.3 格式改动是否有版本号与迁移路径（S6、S7、S8）。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 至少一个场景的遗漏改动静默通过 |
| 1 | 遗漏都能被发现；至少一个场景修改 5 个以上源文件 |
| 2 | 每个场景修改不超过 4 个源文件；遗漏都能被发现 |
| 3 | 每个场景局部于一个模块（加一处注册）；遗漏由编译器发现 |

**出处。** ISO/IEC 25010「可修改性」：可以修改而不引入缺陷、不降低既有质量的程度；「可分析性」：评估一次改动影响范围的有效程度。ATAM 的可修改性场景（刺激、响应、响应度量）。条件变化：通用系统的改动成本以人时计；J++ 的某些改动还带有校准重做与真机复测的成本（`12` §1.4 版本变化时必重测的假设），这部分计入 D6.3 的迁移路径。

### D7 可测试性

**定义。** 每个阶段、每个 pass、每个效应都能在不依赖其他部分、不调用真实判断器的条件下测试，并有真值对照。

**为什么重要。** 三条验收都要求可复核。昂贵测量纪律（`00-定位与方法论` §5.2）要求优先用免费的代理，真机只用于标定；这要求测试层能在固定观察下跑完整条流水线。

**判据。**
- D7.1 是否有不调用网络的客户端（固定观察、重放）覆盖所有效应？
- D7.2 每个 pass 是否有「开 / 关」成对测试，断言出口相同、调用数按预期变化？缺成对测试的已落地 pass 数。
- D7.3 是否有跨实现对照（例如 Rust 内核与 Python 参照实现的出口对照，`tests/cross_kernel*.rs`）？
- D7.4 测试桩的重复度：同一接口的测试桩实现数（S2 计数示范中 41 个测试桩）。数高说明接口过宽或缺共用测试工具。
- D7.5 单测文件能否不经 CLI 直接调用被测阶段？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 至少一个效应只能用真实客户端测试 |
| 1 | D7.1 成立；已落地 pass 中有缺成对测试者 |
| 2 | D7.1、D7.2 成立；无跨实现对照或测试桩无共用工具 |
| 3 | 五项全部成立 |

**出处。** go/analysis 的 `analysistest`（用源码注释 `// want ...` 声明期望诊断）。LLVM `opt-bisect-limit`：pass 自愿接入「可跳过」接口后，可对 pass 序列二分定位引入错误的 pass。FoundationDB 测试文档：在单线程进程内确定性模拟整个集群，「allows perfect repeatability of a simulated run」。条件变化：FoundationDB 模拟的是网络与磁盘故障；J++ 需要模拟的是判断器的读数分布、缺席（`absent`）与漂移，这要求测试客户端能按画像字段产生失败与延迟。

### D8 可观测性

**定义。** 一次运行能导出：分层计划（每层哪些题、为什么在这一层）、每次调用的归因（来自哪个源位置、哪个 pass 合并了它）、每个未决出口的去向、花费与预算余额。导出内容与账本一致。

**为什么重要。** 预算与未决去向是缝，缝由系统接管后，使用者看不到决策过程；没有可观测性，就无法核对「系统替我做的决定对不对」。验收 2 的深度曲线（逐跳一致率与弃权率）也需要逐跳的记录。

**判据。**
- D8.1 是否有等价于 `EXPLAIN` 的计划输出，在不花钱的条件下给出层数与调用数估计？
- D8.2 每次调用能否追溯到源位置与合并它的 pass？
- D8.3 每个 unsure 出口的去向（细化、升级、显式丢弃并记账、转交调用者）是否在运行报告中逐条可见？
- D8.4 报告字段是否全部从账本派生（同一账本重放得到同一报告）？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 只能看到最终出口 |
| 1 | 有调用计数与花费；无分层与归因 |
| 2 | D8.1–D8.3 中两项成立 |
| 3 | 四项全部成立 |

**出处。** PostgreSQL 文档 Planner/Optimizer：计划器产出计划树交给执行器；`EXPLAIN` 展示计划。Go 编译器 SSA README：`GOSSAFUNC` 生成每个 pass 前后的 SSA，「making it easy to see what each pass does」。条件变化：数据库的计划只影响时间；J++ 的计划直接决定花多少钱，所以 D8.1 要求计划输出在执行前可得，而不只是事后的执行记录。

### D9 诊断质量

**定义。** 静态与运行期诊断的结构、稳定性与可操作性。

**为什么重要。** `12` §6.3 与 J-17 规定检查器报文会回喂给生成器（大模型写 `.jpp` 时读报文自修）。报文因此同时面对人和模型，必须结构化、稳定、带可执行的修复建议。

**判据。**
- D9.1 每条诊断是否有：级别、稳定编号（`E-*`/`W-*`/`J-*`）、主源位置、依据条文？缺任一项的诊断种类数。
- D9.2 是否有长说明（类似 `--explain`）按编号可查？
- D9.3 修复建议是否标注可自动应用程度（rustc 的 applicability 四档）？
- D9.4 报文措辞是否禁止疑问句建议（「是不是想……」），直接给出修改？
- D9.5 同一错误在静态面与运行面的编号是否一致？
- D9.6 机器可读输出（JSON）是否存在，供生成器回喂？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 诊断无编号或无源位置 |
| 1 | D9.1 成立；无长说明、无机器可读输出 |
| 2 | D9.1、D9.2、D9.6 成立 |
| 3 | 六项全部成立 |

**出处。** rustc 开发指南 Errors and lints：诊断由级别、编号、主 span、标签、note、help、建议组成；建议带 `MachineApplicable` / `HasPlaceholders` / `MaybeIncorrect` / `Unspecified` 四档；「Suggestions should not be a question」。go/analysis 的 `SuggestedFix`。Elm 的「Compiler Errors for Humans」（2015）常被引用为人读报文的范例，本次抓取失败，未核实原文。条件变化：rustc 报文的读者是人；J++ 报文的读者之一是生成 `.jpp` 的模型，D9.6 因此是必需项而不是加分项。

### D10 性能与惰性语义保持

**定义。** 批处理、提升、推测、向量化等 pass 只改变调用次数、层数与时延，不改变出口、账本内容与副作用。

**为什么重要。** `12` §4 的执行模型是惰性的：效应登记不发，到刷新点才成层发出。性能来自把题并进同一层同一次调用；风险是 pass 改变了语义，例如推测执行了不该执行的 `do`。验收 2 的深度只有在「pass 不改语义」时才能被单独测量。

**判据。**
- D10.1 对照实验：对全部示例程序，在固定观察下跑两臂。两臂都开 `ledger`；对照臂关掉 `lift`、`fuse`、`speculate`、`vectorize`（不用 `Passes::none()`，它连 `ledger` 一起关，两臂记账方式不同）。比较三样：出口；实际执行的 `do` 与 `ask` 调用及其输入，顺序相同；每个结果被实际使用的 `judge` 站点的键与读数。默认臂多出的账本条目只允许是标为推测未用（`W-spec-unused`）的条目。不一致的程序数，目标 0。这一等价只在固定观察下主张；真实判断器上合批是否改变读数属于类假设 H7，另行测试。
- D10.2 推测 pass 是否从不提前执行 `do`、`ask`？有无测试断言这一点？
- D10.3 每个 pass 的收益是否有消融账：关掉它，调用数与层数各变多少？
- D10.4 计划期估计（`plan`）与实际调用数的误差。
- D10.5 解释器自身开销：同一程序在固定观察下的墙钟时间，与调用数之比。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无 pass 开关，或 D10.1 不一致数大于 0 |
| 1 | D10.1 为 0；D10.2 无测试 |
| 2 | D10.1、D10.2 成立；已落地 pass 中有缺消融账者 |
| 3 | 五项全部有数，且 D10.1、D10.2 成立 |

**出处。** Marlow 等，There is no Fork: an Abstraction for Efficient, Concurrent, and Concise Data Access，ICFP 2014（Haxl）：以 Applicative 结构自动把独立的数据请求合批、并发、缓存；本次只读到摘要与检索摘要级内容，未读全文。LLVM `opt-bisect-limit`。条件变化：Haxl 合批的对象是只读数据源，合批天然安全；J++ 的效应中有 `do`（有副作用）与 `ask`（异步问人），推测与合批的安全边界必须按效应种类区分，这正是 D10.2 的来由。

### D11 存储与持久化

**定义。** 账本、校准库、料库、题库、缓存、fit 注册表等持久对象的格式、写入口、版本、迁移与完整性校验。

**为什么重要。** 缝「缓存与增量」与「校准」都依赖持久对象。账本键的等价性决定重放是否成立；校准记录的认证方式与范围（B19、B24）决定一条线能否上岗；长跑与续接程序（`ask` 挂起后恢复）依赖账本可恢复。

**判据。**
- D11.1 每类存储是否有写明的格式定义与版本号（账本头、校准记录头）？
- D11.2 每类存储是否只有一个写入口？写入口数超过 1 的存储类数。
- D11.3 读入时是否校验版本与完整性（哈希、必填字段），不符时拒绝而不是静默降级？
- D11.4 格式变更是否有迁移工具或迁移测试？
- D11.5 存储后端是否可替换（内存 / 文件 / 其他），由一个 trait 隔离？
- D11.6 崩溃一致性：写入中途中断后，重启能否检测并拒绝半写记录？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 至少一类存储无格式定义或无版本号 |
| 1 | D11.1 成立；D11.2 或 D11.3 不成立 |
| 2 | D11.1–D11.3 成立；无迁移或后端不可替换 |
| 3 | 六项全部成立 |

**出处。** Salsa 文档：输入与派生值分开，派生值是输入的确定函数，按修订号判断是否重算。rustc 查询系统：查询结果带依赖图，「makes incremental computation sound」；外部 crate 元数据从 `.rmeta` 读入。条件变化：rustc 与 Salsa 的缓存可以随时丢弃重算，代价只是时间；J++ 的账本条目丢失意味着重新花钱，且新读数可能与旧读数不同（判断器噪声），所以账本不能按缓存处理，D11.6 的崩溃一致性是必需项。

### D12 并发与调度

**定义。** 层内并发、效应之间的调度顺序、并发上限与限流的决策位置与依据。

**为什么重要。** 缝「批调度」与「时延预算」。`12` §4 `schedule` pass 规定 `gen`/`ask` 一登记就先发、`judge` 按层批发、并发按状态大小自适应（取画像 `concurrency`）。Nature #29「五秒钟之内调用几千次」依赖这一处。

**判据。**
- D12.1 调度决策是否集中在一个模块？分散在其他模块中的调度判断位置数。
- D12.2 并发上限、限流、超时是否只取自能力画像字段？写死数值的位置数。
- D12.3 不同效应的调度策略是否由画像字段区分，而不是按效应名分支？
- D12.4 并发执行的结果写入账本时，账本内容是否与串行执行一致（D13 的并发版本）？
- D12.5 缺席（`absent`）与超时的处理是否经 `budget.absent` 路由，与 `E-replay` 分开（`12` §2.3，B35）？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无调度模块；调用按程序顺序逐个发出 |
| 1 | 有层批发；并发参数写死 |
| 2 | D12.1、D12.2 成立 |
| 3 | 五项全部成立 |

**出处。** Sivaramakrishnan 等，PLDI 2021：OCaml 5 以效应处理器表达轻量线程与异步，调度器是用户态库。Marlow 等 ICFP 2014（Haxl）的轮次调度。LLVM 新 pass 管理器文档：禁止内层 pass 触发外层分析计算，以避免二次复杂度并「preserve future concurrency possibilities」。条件变化：OCaml 与 Haxl 调度的目标是吞吐与时延；J++ 还要在同一处权衡花费（预算）与未决率，调度器的输入必须包含预算余额。

### D13 确定性与可重放

**定义。** 给定程序、能力画像版本、校准库版本与账本，重放产生逐字节相同的出口与报告，且不发出任何调用。

**为什么重要。** `12` §2.10 账本键与账本头；`C-模块与标准` §1.3 的「账」模块以「重放逐字节相同」为必要性证据。昂贵测量纪律要求真机结果可以被免费复核，这靠重放。

**判据。**
- D13.1 不确定性来源清单：时间、随机数、环境变量、哈希迭代顺序、线程交错、外部调用。绕过客户端与账本的来源数，目标 0。
- D13.2 重放测试：对全部示例程序，记录一次后重放，比较字节；重放期间调用数必须为 0。
- D13.3 账本缺键时报 `E-replay` 且致命，不进 cause、不挂起；与运行期效应失败 `absent` 分开（`12` §2.3 注）。有无测试？
- D13.4 键与头的分工是否与 `12` §2.10 一致：账本键与缓存键含判断器身份（`model_id`）、规范化状态、题面哈希、渲染版本；账本头含 `profile_hash` 与校准库哈希。校准只把读数映射为出口，不改变读数，所以校准不进键：换校准后重放不重新购买读数，由头的差异报 `W-header`，出口在重放时按读数与线重算。`12` §2.10 的 09-21 订正记录了账本头当时缺校准库哈希（J-18 缺口）；评审时核对它是否已补。
- D13.5 迭代顺序：所有进入账本或报告的集合是否用有序容器或显式排序？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无重放 |
| 1 | 有重放；D13.1 计数大于 0 |
| 2 | D13.1 为 0，D13.2 成立；D13.3 或 D13.4 缺 |
| 3 | 五项全部成立 |

**出处。** rr 项目：记录内核提供给进程的全部输入与少量 CPU 不确定效果，重放时「syscalls return the same data」。FoundationDB 确定性模拟。Salsa「purely deterministic function of its inputs」。条件变化：rr 记录的不确定输入是系统调用返回值；J++ 的不确定输入是判断器读数、生成结果与人的回答，另外还有两个「半静态」输入，即能力画像版本与校准记录版本，它们不随每次调用变化，但变化时会使「重放结果一致」的承诺失效，其中能力画像的哈希记在账本头，校准库的哈希也应记在账本头，二者都不进键，理由见 D13.4。

### D14 安全与信息流（taint）

**定义。** 不可信来源（生成结果、外部材料）的值沿数据流传播的标签，以及在 `do` 站点的检查（J-08）。

**为什么重要。** `do` 会产生副作用。`12` §2.11 规定 taint 代数：`cut` 不产出 taint；J-08 在 `do` 站点执行「条件中至少一个合取项来自 trusted 状态的判断或经 `ask`」。B33 把旁路表改为值级 taint，正是为了让标签与值同行，消除标签丢失路径。

**判据。**
- D14.1 taint 是否是值的一部分（值级），而不是按名字或位置查的旁路表？
- D14.2 值到达 `do` 站点的路径中，不经过唯一 taint 检查点的路径数，目标 0。
- D14.3 taint 的合并规则是否在一处实现（格上的并），各运算符调用它而不各自实现？
- D14.4 控制流依赖（隐式流）是否被考虑：在 tainted 条件下执行的 `do` 是否被检查？
- D14.5 每个 `transform` 与 S 库函数是否声明 `taint_out`，未声明的数目。
- D14.6 是否有绕过测试：构造 tainted 值经各运算符流向 `do`，断言被拒？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无 taint 或 taint 可在某运算符处丢失（有已知反例） |
| 1 | 值级 taint；合并规则分散（D14.3 不成立） |
| 2 | D14.1–D14.3 成立；隐式流或 `taint_out` 声明有缺 |
| 3 | 六项全部成立 |

**出处。** Denning，A Lattice Model of Secure Information Flow，CACM 1976：安全类构成格，流动要求可由格的性质简洁表述，并可据此构造程序认证机制。Wasm 规范：验证后在沙箱中执行。条件变化：Denning 的安全类表示机密性等级；J++ 的 taint 表示来源可信度（生成的、外部的、人答的），流向约束只在 `do` 站点检查，读数经 `cut` 变为出口时不产出 taint。这一差别在 `12` §2.11 有依据，评审时不要按经典机密性模型要求处处检查。

### D15 规范可追溯性

**定义。** 依据条文（`12`、`13`、宪法、J 规则、B 条裁定）与代码、测试之间的双向链接。本维沿用需求工程的术语「孤儿」：正向孤儿指没有任何下游实现或测试链接的条文，反向孤儿指没有引用任何依据条文的代码检查点或测试。

**为什么重要。** `00-定位与方法论` §四 第 3 条「每个设计决定可追溯」，§5.5「隐性知识必须文档化」。代码中一个强制点若找不到它守的条文，后来者无法判断能否删它；一条条文若找不到强制点，它在实现中就不存在。

**判据。**
- D15.1 正向孤儿：依据文本中的规则（J-01…J-18、I、B 裁定中规定行为的条目）没有任何强制点或测试引用它的条数。
- D15.2 反向孤儿：代码中的检查、拒绝、路由分支没有引用任何条文的处数（抽样或 grep `Err(`、`reject`、`W-`/`E-` 报文位置）。
- D15.3 引用格式是否统一且可机器解析（例如 `// 依据：12 §2.3；J-05`），使 D15.1、D15.2 可由脚本算出？
- D15.4 条文改版（v0 → v0.1 → …）后，代码引用是否指向当前版本？指向已被取代版本的引用数。
- D15.5 测试名或测试注释是否引用它检验的条文？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无统一引用格式，孤儿数无法计算 |
| 1 | 可计算；正向或反向孤儿数大于总数的 10% |
| 2 | 两个方向孤儿数都不超过 10% |
| 3 | 两个方向孤儿数为 0，且由脚本在 CI 中检查 |

**取数示范（HEAD 947d4b8）。** 按 `J-NN` 字面 grep：J-01…J-18 中，J-17 在 Rust 源码与测试中引用数为 0，其余 17 条均有源码与测试引用。J-17 规定检查器报文回喂 Python 构建器，其实现位置可能在 Python 侧，是否算正向孤儿需要先确认范围。这一例说明 D15.1 的计算前提是「每条规则登记它的实现范围」。

**出处。** RTCA DO-178C 的双向可追溯要求：正向保证每条需求都被实现和测试，反向保证每行代码和每个测试都有需求依据（依据二手资料 Parasoft、Jama 的综述，未读标准原文）。条件变化：DO-178C 的需求来自系统需求分解；J++ 的依据条文还包括「借用的理论条目」（`00-宪法` 登记表），可追溯链要多一层：代码 → 依据条文 → 理论出处与条件变化。

### D16 代码规范与注释约定

**定义。** 代码风格的自动化程度、公共项的文档注释、注释内容的约定（写依据与状态，不写现状叙事），以及注释与代码的一致性。

**为什么重要。** 方法论 §5.5 要求每个设计元素带六项隐性知识；这些信息的一部分只能写在代码旁边（为什么这里这样判、依据哪条）。同时，§5.5 规定「现状只写黑板，文档不手写现状」，代码注释里的现状叙述会变成过期信息。

**判据。**
- D16.1 格式化与 lint 是否在 CI 中强制（`rustfmt`、`clippy -D warnings`）？被 `allow` 压制的 lint 数。
- D16.2 公共项（`pub`）缺文档注释的数目（`#![warn(missing_docs)]`）。
- D16.3 注释约定是否写成文件：注释写「为什么、依据、替代方案、推翻条件」，不写「目前做到了哪」？
- D16.4 注释与代码的漂移数：注释声称的状态与代码行为不符的处数。
- D16.5 标识符语言约定（中文测试名、英文 API 名等）是否写明且一致。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 无格式化或 lint 强制 |
| 1 | D16.1 成立；D16.4 大于 0 |
| 2 | D16.1 成立，D16.4 为 0；D16.2 或 D16.3 有缺 |
| 3 | 五项全部成立 |

**取数示范（HEAD 947d4b8）。** `jpp-core/src/interp.rs` 的 `Passes` 结构：`enabled()` 的注释把 `lift`、`speculate`、`vectorize` 标为「未落地」，`landed()` 却列出它们；字段注释写 `vectorize`「未落地」，而 `Default` 把它设为 true。结构体文档注释自述「七个 pass 里 core 现在落地两个」，同一注释上方又说按 9 个算。这是 D16.4 能计出的漂移，也说明「注释里写现状」这一做法本身产生漂移。

**出处。** Rust API Guidelines（文档注释章节）；rustc 开发指南关于诊断措辞的约定。Lua 5.0 的「warning-free compilations」目标。条件变化：通用项目的注释约定关心可读性；本项目另有「隐性知识六项」的硬要求，D16.3 按它定义。

### D17 适用场景覆盖

**定义。** 架构对五种运行场景的支持：批处理、交互、长跑与续接、嵌入宿主、离线重放。

**为什么重要。** 目的二是构建以前无法构建的程序：数百道判断连环、`ask` 等人回答、跨会话程序（谈判、长期监控、延迟真值回填，`12` §5 料库条）。这些场景对架构的要求不同：交互要求增量与低时延，长跑要求挂起恢复与账本持久，嵌入要求内核不依赖 CLI 与文件系统。

**判据。** 每个场景一条端到端测试，并回答一个结构问题：
- D17.1 批处理：一次运行处理 N 份材料，调用数随 N 的增长是否符合计划期估计？
- D17.2 交互：修改程序一处后重跑，未受影响的判断是否全部命中缓存？命中率。
- D17.3 长跑与续接：`ask` 挂起后进程退出，重启从账本恢复，已发调用不重发？
- D17.4 嵌入宿主：内核能否作为库被调用，不经 CLI、不读写固定路径？公共 API 是否足以完成一次运行？
- D17.5 离线重放：无网络、无凭据时重放全部示例？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | 只支持一种场景 |
| 1 | 支持两到三种，缺端到端测试 |
| 2 | 四种有端到端测试 |
| 3 | 五种有端到端测试，且 D17.2 命中率有数 |

**出处。** Lua 5.0 论文：「Embeddability: Lua is an extension language」，要求简单而强的 C API、低嵌入成本。Roslyn 概述：编译器作为 API，语法树不可变、线程安全，支持工具共享编译器的信息。Salsa 与 rustc 查询系统的增量重算。条件变化：Lua 与 Roslyn 的嵌入对象是同步调用；J++ 的一次运行可能跨越数天（等人回答、等真值回填），嵌入接口必须暴露挂起与恢复，而不只是「给程序、拿结果」。

### D18 规模经济

**定义。** 实现与其说明文档的体量关系，以按方向可比的量衡量。

**为什么重要。** 目的一是构建更便宜。对实现本身，同样的要求是：维护者完成一次改动要读的东西少，文档不会与代码背离。

**判据。**
- D18.1（报告项，不打分）文档行数 / 代码行数。HEAD 947d4b8：Rust 源码约 12,500 行（`jpp-core` 约 10,300、`jpp-frontend` 约 1,200、`jpp-cli` 约 1,000），测试约 11,900 行。文档行数需先划定「架构文档」的范围再计。
- D18.2（打分项）最小阅读集：对 S1–S10 每个场景，完成改动前必须读的文档与代码行数的中位数。越小越好。
- D18.3（打分项）漂移密度：每千行代码对应的文档与代码不一致处数（D16.4 与架构文档陈述的合计）。越小越好。
- D18.4 单个设计决定的说明是否只出现在一处（其余位置链接过去）？同一事实被独立重复陈述的处数（`Passes` 注释自述「同一过期数字在三处独立写着」即此类）。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | D18.2 无法计算（没有能指向某个场景的文档入口） |
| 1 | D18.2 中位数超过 3,000 行，或 D18.3 超过 2 |
| 2 | D18.2 中位数 1,000–3,000 行，D18.3 不超过 2 |
| 3 | D18.2 中位数不超过 1,000 行，D18.3 为 0，D18.4 为 0 |

刻度中的行数阈值是本版的初始假设，第一次评审取数后按实际分布修订，修订记入 §八。

**出处。** Lua 5.0 论文：「We seek the simplest language we can afford and the simplest C code that implements this language」，核心小于 100 KB。Keep & Dybvig 2013：nanopass 若缺少样板代码的自动生成，会「increasing compiler size and thus failing to decrease maintenance and extension overhead」。条件变化：Lua 以代码体积衡量简单；J++ 的维护成本大头是依据文本与代码之间的对齐，所以打分量选阅读集与漂移密度，不选代码体积。

### D19 缝的接管

**定义。** 八条缝（批调度、深度与终止、未决去向、预算、缓存与增量、校准、判断力缺席、时延预算）是否由编译器与运行时决定，使语义等价的不同写法得到相同或有界差距的执行代价。

**为什么重要。** `00-定位与方法论` §三：语言的本体是八条缝；若某种写法能让使用者无意中绕过批处理，说明该缝仍由使用者承担。`16` §一 记录同一份材料问十四个问题，两种写法调用次数相差十四倍。

**判据。**
- D19.1 等价写法对：为每条缝构造至少一对语义等价、写法不同的程序（例如列表推导式与过滤算子）。每对的调用数之比、花费之比、层数之比。
- D19.2 上界：各对比值的最大值。本版提议上界为 1.5（待首次评审后按分布修订）。
- D19.3 每条缝在实现中由哪个模块决定？找不到决定模块的缝数。
- D19.4 使用者能否在程序中写出绕过缝的指令（例如手写并发数、手写阈值）？能写且不被检查拒绝的缝数。

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | D19.3 找不到决定模块的缝超过 4 条 |
| 1 | 至少一对等价写法的调用数之比超过 3 |
| 2 | 所有对的比值不超过 3；D19.3 或 D19.4 计数大于 0 |
| 3 | 所有对的比值不超过上界；八条缝各有决定模块；D19.4 为 0 |

**出处。** `00-目标与动机` §3（SQL 的连接顺序由规划器决定、Verilog 布线由综合器决定）。PostgreSQL 计划器文档：同一查询有多种执行方式、结果相同，由优化器选代价最低者。Graefe 1995 Cascades。条件变化：SQL 规划器面对的是确定的关系运算，代价只有时间；J++ 的等价写法还要求未决出口集合相同，代价包括钱与未决率，所以 D19.1 要同时比较三个量。

### D20 能力画像隔离

**定义。** 判断器的价格、时延、并发、窗口、已知缺陷只以能力画像字段出现，语言规则与内核代码只引用字段名。

**为什么重要。** 预言 1、验收 3「换接口，程序一个字不改」、跑偏清单第 3 条「把当前判断器的价格或缺陷写进语言规则而非画像」。`00-目标与动机` §2 称这一条「是这门语言活得比 Jev 久的唯一机制」，并给出实测：两份只差 `arithmetic_capable` 一个字段的画像，同一 `.jpp` 一份 J-01 报 error、一份降 warn。

**判据。**
- D20.1 内核与检查器中写死的判断器数值（价格、并发、窗口 token 数、K 上限）的位置数，目标 0。
- D20.2 按判断器名字（如 `"jev"`）分支的位置数，目标 0。
- D20.3 画像交换测试：对全部示例程序，换 `12` §1.2 的每一条类假设对应字段，程序文本不改能跑；覆盖的类假设条数 / 总条数。
- D20.4 画像字段的默认值是否集中在一处且标明来源（实测编号）？
- D20.5 新增画像字段（S10）是否只改画像定义与读取它的规则？

**刻度。**
| 分 | 可观测事实 |
|---|---|
| 0 | D20.1 或 D20.2 大于 0，且其中至少一处影响出口 |
| 1 | D20.1、D20.2 大于 0，但只影响性能 |
| 2 | D20.1、D20.2 为 0；D20.3 覆盖不全 |
| 3 | 五项全部成立，D20.3 覆盖全部类假设 |

**出处。** LLVM `TargetMachine` 与目标描述（后端差异经目标描述表达，中端 pass 不按目标名分支）；本次未单独抓取该文档，依据为 LLVM 新 pass 管理器文档中的 `TargetMachine::registerPassBuilderCallbacks()`。条件变化：LLVM 的目标差异在编译时已知且固定；判断器画像会随版本变化（`12` §1.4），画像字段还必须带「何时重测」的信息。

## 六、打分与汇总

**门槛维度。** D4 不变量强制点、D10 性能与惰性语义保持、D13 确定性与可重放、D14 安全与信息流、D19 缝的接管、D20 能力画像隔离。这六维任一低于 2 分，架构方案不得定稿。选择理由：前四维对应语义承诺（出错会产生错误的结果或错误的副作用，且不易察觉）；后两维对应「为什么必须是语言」的论证本身。

**非门槛维度。** 报告各维得分与取数依据，不求加权和。评审结论写「哪几维低于 2、最小修复是什么」，而不是一个总分。理由：各维不可相互抵偿，D18 满分不能弥补 D13 零分。

**评审报告格式。** 每维一行：得分；每条判据的取数结果（数值或是/否）；取数命令或文件位置；提交号。取数不了的判据写「不可计算」及原因，不估分。

**评审时机。** `20-架构方案-v1.md` 定稿前按方案文本评一次（评「方案承诺」）；施工完成一个阶段后按代码评一次（评「实际状态」）。两次结果的差即方案与实现的差距。

## 八、本标准的隐性知识（按方法论 §5.5 六项）

1. **为什么要它。** Nature 2026-09-23：「评论架构好不好，评论，特别是评论一个编程语言的架构好不好，应该是有很详细的标准的。啊，我们可以去符合那个标准去来做，然后做不好我们再修就好了嘛，对吧。」`17` 阶段 1.5 规定架构方案经三视角对抗评审，评审需要共同的尺度。
2. **考虑过的替代与放弃理由。** 其一，直接采用 ISO/IEC 25010 的质量特性打分：放弃，因为它不含缝、画像、读数这类 J++ 特有概念，D19、D20 在其中找不到位置。其二，只用 ATAM 现场会评：放弃作为唯一方法，因为 ATAM 依赖利益相关方现场讨论，本项目评审者多为代理，需要可由命令取数的判据；保留其「质量属性场景」做法作为 §三。其三，给各维加权求总分：放弃，理由见 §六。
