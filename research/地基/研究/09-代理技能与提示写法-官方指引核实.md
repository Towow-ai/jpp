# 09 · 写给代理用的 skill 与提示：Anthropic 官方指引核实（2026-09-24）

调研问题：给 Opus 5.5 / Sonnet 5 这类代理配一份「怎么写 J++」的 skill，官方规定的格式是什么、正文该写什么、怎么验证有效。用途：`评估/2026-09-24-仪表读数4诊断与裁定.md` §五（B97）定 skill 的结构。一手来源（2026-09-24 经 Jina 取正文，本地 `claude-api` skill 与 `~/.agents/OPUS-5.5.md` 作对照）：

- Anthropic 文档《Agent Skills》概述：`docs.claude.com/en/docs/agents-and-tools/agent-skills/overview`
- 《Skill authoring best practices》：`docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices`
- 开放规范《Agent Skills Specification》：`agentskills.io/specification`
- Anthropic 工程文章《Equipping agents for the real world with Agent Skills》（2025-10，附注 2025-12-18 开放标准）
- 《Prompting best practices》（Claude 4 系列至 Fable 5.1 / Opus 5.5 通用页）：`docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices`
- Claude Code《Skills》页（frontmatter 扩展字段、动态注入）：`docs.claude.com/en/docs/claude-code/skills`
- 本机：`~/.agents/OPUS-5.5.md`（官方迁移指南的整理）、官方插件 `skill-creator` 的 `SKILL.md`

## 一、格式：官方规定的部分

| 项 | 规定 | 出处 |
|---|---|---|
| 目录 | 一个目录，至少含 `SKILL.md`；可选 `scripts/`（可执行）、`references/`（按需读的文档）、`assets/`（模板、数据） | 规范 |
| frontmatter 必填 | `name`（≤ 64 字符，小写字母、数字、连字符，须与目录名相同，不含 anthropic/claude）、`description`（≤ 1024 字符，写清**做什么**与**何时用**，含触发关键词） | 概述、规范 |
| frontmatter 可选 | `license`、`compatibility`（≤ 500 字符，环境要求）、`metadata`（字符串键值表）、`allowed-tools`（实验） | 规范 |
| Claude Code 扩展 | `when_to_use`（追加到 description，二者合计截断于 1,536 字符）、`disallowed-tools`、`model`、`context: fork` 加 `agent`、`arguments`/`$ARGUMENTS`、`paths`（目录限定）、**动态注入**：正文里以 `!` 开头的 shell 命令在 skill 装载时执行，输出替换进正文 | Claude Code Skills 页 |
| 正文 | 无格式限制；推荐分步指令、输入输出示例、常见边界；**装载即整份进上下文**，长内容拆到引用文件 | 规范 |
| 分级装载 | 一级：所有 skill 的 name + description 常驻（每个约 100 token）；二级：触发后读 `SKILL.md` 正文（建议 < 500 行、< 5k token）；三级：`references/`、`scripts/` 按需读或执行，脚本只有输出进上下文 | 概述、规范、工程文章 |
| 引用深度 | 引用文件与 `SKILL.md` 只隔一层；> 100 行的引用文件顶部放目录 | 最佳实践 |
| 命名 | 动名词优先（`processing-pdfs`），或名词短语；避免 `helper`、`utils` | 最佳实践 |

## 二、正文该写什么：官方的写作原则

1. **只写 Claude 不知道的。** 上下文是公共资源；每段先问「Claude 已经知道吗」。对通用知识（PDF 是什么、库怎么用）不解释。
2. **自由度按脆弱程度定。** 多种做法都对、依上下文判断的事用文字指引（高自由度）；有推荐模式的用带参数的伪码或脚本（中）；顺序不能错、易出错的操作用固定脚本（低）。
3. **描述字段决定触发。** 官方与 `skill-creator` 都指出 Claude 倾向少触发，description 要写得「推一点」：列出用户可能说的词，即使他没明说要用这个 skill。
4. **工作流写成步骤与清单**；质量关键处放反馈回路：跑校验器 → 改 → 再跑。校验器可以是脚本，也可以是一份参照文档。
5. **术语一致、不写会过期的内容**（版本、日期、当前限额一律不进正文；旧模式放「old patterns」段）。
6. **模板与示例**：输出格式严格时给模板；靠示例才说得清的给输入输出对，用 `<example>` 包起来。
7. **不列多个可选做法**，除非确有必要；脚本要自己处理错误，不把判断推回给 Claude；常数要说明来历。
8. **先做评测再写文档**：先在代表性任务上不带 skill 跑一遍记下失败，据此写三个评测场景，量基线，再写最少的指引让评测通过，迭代；在打算用的每个模型上都测（Haiku 要更多指引，Opus 要避免过度解释）。开发时一个实例写（Claude A）、另一个实例用（Claude B），按 B 的实际行为改。
9. **观察导航路径**：Claude 读文件的顺序、漏掉的引用、反复读的段落、从不读的文件，都是结构信号。

## 三、提示写法里与 skill 直接相关的几条

- **说明动机有效。** 官方原文：「Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can help Claude better understand your goals and deliver more targeted responses.」这是 Nature「skill 要写为什么」的官方依据：为什么这么设计随原则变、很少随实现变，写进 skill 不构成第二个维护点。
- **明确、直接、具体**：要什么输出、什么约束，说清楚；用 XML 标签分隔指令、语境、示例、输入。
- **Opus 5 / 5.5 的调整**：不再加「最后再验证一遍」「用子代理复核」这类脚手架（会过度验证）；范围纪律用官方那段「Deliver what the user asked for, at the scope they intended…」；子代理克制；为旧模型调过的约束逐条复测，不原样搬（`~/.agents/OPUS-5.5.md` §三）。
- **Opus 5.5 只用 effort 控制思考，默认 `medium`**；写 skill 时不要求它「多想」或「别想」，降档比提示词可靠。
- **审查类任务不要设严重度过滤**（「只报高危」会压低召回）；对写程序代理的验收，让它报全部诊断再筛。

## 四、对 J++ skill 的直接推论

1. **两类内容分开放，来源不同。** 随实现变的（内置签名、返回形状、最小示例、报错修法）由 `jpp describe`/`jpp explain`/`check --json` 生成，skill 正文用动态注入 `!jpp describe --md` 或引用 CI 生成的 `references/describe.md`，不手抄；随设计原则变的（读数只经桥、未决要转交、线从真值来、为什么合批、taint 为什么拦不可逆 `do`）写进正文的「为什么」段，每条标 `00`/`12` 条款号。
2. **正文控制在 150 行内**：description（触发词含 `.jpp`、`jpp run`、J++、JEV 判断、写探针程序）、为什么（8–10 条）、固定流程（先跑哪几条命令、按什么顺序写、遇诊断怎么办）、禁则、验收方式。签名表不进正文。
3. **反馈回路就是 `jpp check --json` 的 `fix` 字段**：写 → check → 按 fix 改 → run → 看报告里的 `pending`。
4. **评测先行**：31-1 的非设计者批就是「不带 skill 的基线」；31-3 是带 skill 的评测，指标事先预注册（行数比设计者版、验收一次通过率、丢弃写法出现次数、调用数比、墙钟）。
5. **跨工具**：按开放规范写（只用 `name`/`description`/`metadata` 与正文），Claude Code 的动态注入作可选增强，Codex 等其他宿主用 CI 生成的引用文件。

## 五、边界

- 官方文档未给出「skill 正文写设计原理」的直接范例；依据是 §三第一条的动机原则与最佳实践里「只写 Claude 不知道的」——J++ 的设计原则正是模型不知道的东西。
- 动态注入是 Claude Code 扩展，不在开放规范里；skill 若要在 Codex 侧同样可用，须保留生成文件那条路。
- 各页的字数上限（500 行、5k token、1,536 字符）取自 2026-09-24 当日页面，将来以页面为准。
