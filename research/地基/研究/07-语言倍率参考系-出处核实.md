# 语言倍率参考系：出处核实

2026-09-24 调研。问题来自验收①的委托：「如果 C++ 比 C 好用 20 倍，那么我们的新语言也可以这样去比对，这种比对应该是有标准的。」本文收集业界和学界有出处的语言间倍率，供制定验收标准时作参考系。

本文与 [`地基/评估/语言表达量对比-方法与参考倍率.md`](../评估/语言表达量对比-方法与参考倍率.md) 互补。那份文档已整理计量方法和 Jones 1996、QSM、Prechelt 的主要数字。本文另外核实并补充以下来源：Jones 2017 的 79 种语言表、Stroustrup 1999 的行数对比、Prechelt 原始数据的逐语言中位数、Rust 相关的三份数据、Brooks 与 Corbató 的历史数据、IBM 汇编对 PL/S 的数据、UNIX 用 C 重写的记录，以及 Pig Latin 的数字。

每个数字都附来源链接。查不到可核实出处的写「未查到」。凡是用表中数字相除得到的比值，标「自算」。倍率分三种度量：代码量、开发工时、团队投入，三者不能混读。例如 Jones 表中 2.4 倍的代码量差距，不等于 2.4 倍的生产力差距。

## 总览

没有查到「C++ 比 C 好用 20 倍」的任何出处，Stroustrup 本人也没有给过整体生产力倍率。通用语言之间有出处的倍率，代码量都在 1–3 倍，开发工时约 2–3 倍。10 倍及以上只出现在专用语言对通用语言的对比中：Jones 表中 C 对 SQL 约 9.8 倍（代码量），机器语言对 C 为 5 倍。本次查到的唯一 20 倍数字，是 Pig Latin 对 Java MapReduce 的单个任务，来自二手课件。

## 1. C 对 C++

### 1.1 Capers Jones / SPR《Programming Languages Table》Release 8.2（1996 年 3 月）

C 为 2.5 级，每功能点（FP）128 条语句；C++ 为 6.0 级，每 FP 53 条语句。按代码量，C 约为 C++ 的 2.4 倍（自算：128/53）。

- 出处（Wayback 存档）：http://web.archive.org/web/20000821235231/http://www.spr.com:80/library/0langtbl.htm
- 镜像：https://www.cs.bsu.edu/homepages/dmz/cs697/langtbl.htm

「语言等级」按定义就是代码量比例。原文举例：COBOL（3 级）写 1000 条语句的应用，用 6 级语言约需 500 条，用 12 级语言约需 250 条。Prechelt 也指出，表中等级乘以每 FP 语句数恒约为 320。

Jones 在同一页给出三条限定，引用这张表时应一并带上：

1. 生产力与语言等级不成线性。编码约占大型项目工作量的 30%；语言等级翻倍，编码工作量减半，整个项目只省约 15%；再翻倍只再省约 7.5%。
2. 表 1 直接给出按等级划分的生产力区间（FP/人月）：

   | 语言等级 | 生产力（FP/人月） |
   |---|---|
   | 1–3 | 5–10 |
   | 4–8 | 10–20 |
   | 9–15 | 16–23 |
   | 16–23 | 15–30 |
   | 24–55 | 30–50 |
   | 55 以上 | 40–100 |

   按区间中点折算，C（2.5 级）到 C++（6 级）约为 2 倍（自算）。
3. 各语言等级的来源不一。只有 Ada、BASIC 方言、COBOL、PASCAL、PL/I 实测过功能点和代码。汇编、C、LISP 等是把源码量与 COBOL 对比得出的。ACTOR 等是检查源码后主观推断的。KL、CLOS 等只是阅读语言描述后估计的。

### 1.2 QSM Function Point Languages Table 5.0（2013）

依据 2192 个单语言完工项目，按逻辑 SLOC 计。C 的均值为 97、中位数为 99，C++ 为 50 和 53。C 约为 C++ 的 1.9 倍（自算：均值比 1.94，中位数比 1.87）。

- 出处：https://www.qsm.com/resources/function-point-languages-table
- 发布稿：https://www.qsm.com/press-release/qsm-releases-function-point-languages-table-50

### 1.3 Jones 2017，Table 16

出自《Software Economics and Function Point Metrics: Thirty years of IFPUG Progress》v10.0。实现 1000 FP，C 需 128 KLOC、26,273 工时，C++ 需 53.33 KLOC、12,697 工时，工时比为 2.07 倍（自算）。这些工时由「固定 3000 小时非编码工作，加按 LOC 比例计算的编码工时」推算得出，作者说明只作示意，不能当作独立实测。

- 出处：https://www.ifpug.org/wp-content/uploads/2017/04/IYSM.-Thirty-years-of-IFPUG.-Software-Economics-and-Function-Point-Metrics-Capers-Jones.pdf

### 1.4 Stroustrup〈Learning Standard C++ as a New Language〉，C/C++ Users Journal，1999 年 5 月

文中比较了两个小程序的 C 风格与 C++ 风格写法：

- 例 1：C 风格 41 行，C++ 风格 10 行。去掉脚手架代码后为 30 行对 4 行。对所需讲解的概念数量，他写的是「I suggest a 10-to-1 advantage」，属主观估计。
- 例 2：43 行对 24 行（非空行）。去掉共同部分后为 20 行对 11 行，其中排序部分为 9 行对 1 行。

文中的「a factor of 3, 10, or even 50」指人们愿意为便利付出的性能代价，不是生产力倍率。

- 出处：https://www.stroustrup.com/new_learning.pdf

他在 FAQ 中只给出定性说法：「I never saw a project for which C was better than C++ for any reason but the lack of a good C++ compiler.」（https://www.stroustrup.com/bs_faq.html）。Stroustrup 给出的整体生产力倍率：未查到。

### 1.5 反例：Prechelt 2000 的原始数据

技术报告附录 A 列出了全部原始数据，按中位数自算：C 为 244 行、8.2 小时（n=5）；C++ 为 243 行、11.2 小时（n=11）。在这个任务上，C++ 的代码量与 C 持平，工时反而更长。论文正文没有单独比较 C 与 C++，C 的样本也只有 5 个。

- 出处：http://page.mi.fu-berlin.de/prechelt/Biblio/jccpprtTR.pdf

## 2. Rust 对 OCaml、Rust 对 C

Rust 对 OCaml 的严肃实证研究：未查到。Jones 1996、Jones 2017、QSM 三张表都没有收录 Rust 和 OCaml。以下三份数据可作参考，证据强度都较弱。

**Tristan Hume 2019 年的博客。** 滑铁卢大学 CS444 课程要求各队用自选语言，把 Java 的一个子集编译为 x86。以 Hume 所在的 Rust 队为基准（6806 行，wc -l），其他队的代码量如下：

- OCaml 队为 1.0–1.6 倍，视计法而定；去掉解析器设计差异后约 1.15 倍。
- C++ 队为 1.4 倍，Haskell 队为 1.0–1.6 倍，Python 约 0.5 倍，Scala 为 0.7 倍。
- 另一支 Rust 队为 3 倍，同一语言内部的差距反而最大。

每种语言只有一个样本，属于轶事证据。出处：https://thume.ca/2019/04/29/comparing-compilers-in-rust-haskell-c-and-python/

**Ardito 等 2021（PeerJ Computer Science 7:e406）。** 比较了 9 个 Benchmarks Game 算法的多语言实现。表 8 的均值：C 的 SLOC、PLOC、LLOC 为 209、129、48，Rust 为 144、105、52。由此自算，C 对 Rust 在 SLOC 上为 1.45 倍，在 PLOC 上为 1.23 倍，在 LLOC 上为 0.92 倍，即 Rust 的逻辑行反而更多。论文正文写 Rust 的 PLOC 为 74，与表 8 的 105 矛盾，本文以表为准。出处：https://peerj.com/articles/cs-406/

**Google 的 C++ 改写为 Rust。** 这一条是 C++ 对 Rust，不是 C 对 Rust。Google 工程总监 Lars Bergstrom 在 Rust Nation UK 2024 上说，C++ 服务改写成 Rust 后，「In every case we've seen a decrease by more than 2x in the amount of effort」，涵盖开发与维护；Go 改写成 Rust，团队规模和耗时大致不变。这是未公开的内部数据，度量的是团队投入。出处是 The Register 的转述：https://www.theregister.com/2024/03/31/rust_google_c

## 3. C 对 Java

两张功能点表给出的倍率在 2 倍左右，Rosetta Code 和 Prechelt 的实际程序数据则接近 1 倍：

- Jones 1996：Java 为 6.0 级、每 FP 53 条语句，C 为 2.5 级、128 条。C 约为 Java 的 2.4 倍，按生产力区间折算约 2 倍（自算）。
- QSM 5.0：Java 的均值和中位数都是 53，C 约为 Java 的 1.8–1.9 倍（自算）。
- Nanz & Furia，ICSE 2015（arXiv 1409.0252）：Rosetta Code 上 745 个任务、7087 份解答。表 19 按每个任务取最短解，C 对 Java 的比值 R=1.03，几乎相同；Java 比函数式语言和脚本语言长 2.2–2.9 倍。出处：https://arxiv.org/abs/1409.0252
- Prechelt 原始数据（自算）：C 与 Java 的中位行数都约为 244 行，比值为 1.0。
- Jones 2017：Java 为 53.33 KLOC，与 C++、Go、PHP、Python 同档。

## 4. C 对 Python/Perl

### 4.1 功能点表

- Jones 1996：Perl 为 15 级、每 FP 21 条语句，C 约为 Perl 的 6.1 倍（自算）。表中没有 Python。
- Jones 2017：实现 1000 FP，Python 需 53.33 KLOC，Perl 需 35.56 KLOC。C 对 Python 为 2.4 倍，C 对 Perl 为 3.6 倍（自算）。Jones 本人把 Perl 从 1996 年的每 FP 21 条改成了 35.56 条。
- QSM 5.0：Perl 均值 24、中位数 15，C 对 Perl 为 4.0 倍（均值）或 6.6 倍（中位数）（自算）。表中没有 Python。

### 4.2 Prechelt〈An Empirical Comparison of Seven Programming Languages〉，IEEE Computer，2000 年 10 月

实验收集了 80 个 phonecode 程序。结论原文：「Designing and writing the program in Perl, Python, Rexx, or Tcl takes no more than half as much time as writing it in C, C++, or Java—and the resulting program is only half as long.」

- 工时中位数：脚本组 3.1 小时，C/C++/Java 组 10.0 小时，约 3.2 倍。
- 长度：「Nonscripts typically are two to three times longer than scripts.」
- 逐语言中位数（自算）：Python 82 行、2.83 小时，Perl 74 行、2.83 小时。C 对 Python 在行数上为 3.0 倍，在工时上为 2.9 倍。

这组数据有两条限定。第一，脚本组的工时由程序员自报，C/C++/Java 组的工时由实验者测量，两组程序员的来源也不同。第二，作者指出同一语言内部程序员之间的差异（最慢一半与最快一半的中位数之比，工时上为 1.5–3.2）与语言之间的差异一样大，甚至更大。

- 出处：https://www.cs.tufts.edu/~nr/cs257/archive/lutz-prechelt/comparison.pdf

### 4.3 Nanz & Furia，Rosetta Code

表 19 中 C 对 Python 的比值 R=2.9，原文为「the average C solution is over 2.9 times longer in lines of code than the average Python solution」。

### 4.4 一处引用错误

Prechelt 技术报告的表 3 引用 Jones 表时，把 C 写成 3.5 级、每 FP 91 条语句，与 SPR 存档中的 2.5 级、128 条不符。本文以 SPR 存档为准。

## 5. 汇编对 C

### 5.1 功能点表

- Jones 1996：Basic Assembly 为 1.0 级、每 FP 320 条语句，Macro Assembly 为 1.5 级、213 条，Machine language 为 0.5 级、640 条。自算得汇编对 C 为 2.5 倍，宏汇编对 C 为 1.67 倍，机器语言对 C 为 5 倍。按表 1，汇编（1 级）与 C（2.5 级）同在 1–3 级区间（5–10 FP/人月），生产力区间上看不出差别。
- QSM 5.0：Assembler 均值 119、中位数 98，C 为 97 和 99。汇编对 C 为 1.23 倍（均值）或 0.99 倍（中位数）（自算），与 Jones 的 2.5 倍相差约 2 倍。
- Jones 2017 Table 16（推算工时）：Basic Assembly 61,182 小时，C 26,273 小时，为 2.33 倍（自算）。

### 5.2 历史数据

汇编改写为 C 的开发时间实测：未查到。以下三条历史数据与此相关，但度量不同，都不是汇编对 C 的开发时间。

**IBM 编译器，约 1968–1975 年。** 见 Jones 2017 表 1，作者说明表中用的是「simple round numbers」。汇编版为 17,500 LOC、30 人月，PL/S 版为 5,000 LOC、12.5 人月，生产力分别为 3.33 和 8.00 FP/月。自算得代码量为 3.5 倍，工作量为 2.4 倍。PL/S 不是 C。

**Brooks《人月神话》第 8 章〈Corbató's Data〉。** MULTICS 的平均生产力为每人年 1200 行调试通过的 PL/I，每条语句约相当于 3–5 个手写机器字。原文结论有两条：「Productivity seems constant in terms of elementary statements」，以及「Programming productivity may be increased as much as five times when a suitable high-level language is used」。这是 PL/I 对汇编，不是 C 对汇编。第 16 章〈No Silver Bullet〉中「at least a factor of five」的原文是「Most observers credit」，属于共识陈述，不是测量结果。

- 课程托管副本：https://bowringj.people.charleston.edu/classes/csis%20602/docs/The.Mythical.Man.Month.F.Brooks.pdf

**Ritchie & Thompson 1974，CACM〈The UNIX Time-Sharing System〉。** 1973 年夏天用 C 重写后，「The size of the new system is about one third greater than the old」，同时加入了多道程序等新功能。这里比的是系统体积，而且 C 版更大。

- 出处：https://dsf.berkeley.edu/cs262/unix.pdf

## 6. SQL 对手写代码

同一任务下 SQL 对手写循环的受控测量：未查到。可用的只有功能点表的间接推算和一个单任务数字。

- Jones 1996：SQL、ANSI SQL、Query default 都是 25 级、每 FP 13 条语句，C 对 SQL 为 9.8 倍（自算）。按表 1，24–55 级为 30–50 FP/人月，C 为 5–10，按中点折算约 5 倍（自算）。
- QSM 5.0：SQL 均值和中位数都是 21。C 对 SQL 为 4.6–4.7 倍，Java 对 SQL 为 2.5 倍（自算），与 Jones 相差约 2 倍。
- Jones 2017：TranscriptSQL 为 12.80 KLOC/1000 FP、5,327 小时。C 对它在代码量上为 10 倍，在推算工时上为 4.9 倍（自算）。

**Pig Latin 对 Java MapReduce。** 统计出现频率最高的 5 个词这一任务：10 行对 200 行，15 分钟对 4 小时，即代码量 20 倍、时间 16 倍。出处是二手课件（Hui Li、Judy Qiu，改编自 Adam Kawa 2012 年的材料），通常归于 Yahoo 的 Pig 团队，原始出处未找到。这是单个任务的宣传式数字。

- 出处：https://www.slideserve.com/ziva/high-level-language-pig-latin

**Harel & McLean 1985（MIS Quarterly 9(2):109–120）。** 6 个应用分别用 COBOL 和 FOCUS（一种第四代语言）实现，两边由水平相当的程序员配对。摘要只写「programmed significantly faster」，没有给出倍数。搜索摘要里出现过「约三倍」，但在论文摘要原文中找不到，倍数记为未查到。

- 出处：https://doi.org/10.2307/249112

**反例：Welty & Stemple 1981（ACM TODS 6(4):626–649）。** 比较 SQL 与更偏过程式的 TABLET，结论是用更偏过程式的语言写难查询写得更好。论文没有给出倍率。

- 出处：https://doi.org/10.1145/319628.319656

## 7. 来源之间的分歧

同一对语言在不同参考系下常差约 2 倍，引用时要标明用的是哪张表：

| 语言对 | Jones 1996 | Jones 2017 | QSM 5.0 |
|---|---|---|---|
| 汇编 → C | 2.5× | 2.33×（推算工时） | 0.99–1.23× |
| C → SQL | 9.8× | 10×（TranscriptSQL） | 4.6–4.7× |
| C → Perl | 6.1× | 3.6× | 4.0–6.6× |
| Excel（每 FP 条数） | 约 6 | 6.40 KLOC/1000 FP | 均值 209 |

同一参考系内部也会改数，例如 Jones 2017 把 Python 与 C++、Java 放在同一档，把 Perl 从每 FP 21 条改为 35.56 条。

Prechelt 和 Hume 都发现，同一语言内部不同程序员或团队之间的差异，与语言之间的差异一样大，甚至更大。用单个实现对比两门语言时，这项噪声可能盖过语言本身的差异。
