## 二、共性做法

版本记录和社区摘要是两层不同的东西，节奏也不同。Release notes、CHANGELOG 跟着版本走，不定期（BAML、Outlines、Gleam、Dify 都是这样）；社区摘要跟着日历走，固定周期（[This Week in Rust](https://this-week-in-rust.org/blog/2026/06/03/this-week-in-rust-654/) 每周，[marimo](https://marimo.io/blog/newsletter-22) 每月）。前者服务已经在跟的人，后者的作用是让没有每天看仓库的人也能在固定时间点知道项目还活着、往哪走。J++ 现在的 `docs/updates/`（16 篇，公开、从 README 可达）和 `docs/progress.md` 已经承担了前一层，且比大多数调研到的项目记录得更细；缺的是后一层：固定周期、单一可订阅入口的摘要。

每条通报的结构高度收敛到四项：改了什么、怎么试、谁做的、下一步。顺序和详略各项目不同，但这四项几乎在每个例子里都出现：[BAML](https://boundaryml.com/blog/baml-0.19.0) 给升级命令，[Outlines](https://github.com/dottxt-ai/outlines/releases/tag/1.0.0) 给迁移指南链接，Gleam 和 BAML 都具名致谢，[DSPy 路线图](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/roadmap.md) 和 [This Week in Rust](https://this-week-in-rust.org/blog/2026/06/03/this-week-in-rust-654/) 都把下一步写成可认领的具体条目。J++ 的 `docs/maintaining.md` 已经内部规定了同样四项（改变及效果、使用命令、验证及限制、下一步、commit 链接）——这个结构不需要新造，只需要把已经在用的内部结构套一层对外的摘要格式。

公开写清楚哪里没做到，是这些项目正文里的常规内容，不是附加的免责声明。[BAML](https://boundaryml.com/blog/baml-0.19.0) 直接写「这不是吞吐量或端到端延迟基准」；[Outlines](https://github.com/dottxt-ai/outlines/releases/tag/1.0.0) 明说某功能已弃用且无替代；[Modular](https://www.modular.com/blog/mojo-open-source) 在宣布编译器开源的同一篇博客里说明「暂不接受编译器和工具链的贡献，目标是年底前开放」；坦白程度最高的一例是 [LobeHub 的讨论帖](https://github.com/lobehub/lobehub/discussions/10007)——公开承认两年前的架构选型判断有误，帖子的评论区随后很活跃，用户主动追问升级路径和发布时间，维护者直接回复。这与「诚实是基础，不是放弃的理由」（`地基/00-定位与方法论-v1.md` 六）的判据一致：写清楚哪里没做到，换来的是社区认真参与讨论。

研究期的参与邀请靠具体、可认领的小任务。[This Week in Rust 的 Call for Participation](https://this-week-in-rust.org/blog/2026/06/03/this-week-in-rust-654/) 逐条给出项目名+具体 GitHub issue 链接（例如「MD Preview——为 Homebrew Cask 打包」）；[DSPy 路线图](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/roadmap.md) 的邀请方式也直接是「开一个 issue 或提一个 PR」。J++ 自己的 `CONTRIBUTING.md` 已经写了同样的判断——「一个能运行的小方法教给我们的东西，比一份宏大的功能清单更多」——这个共识已经在项目里，只是还没有转成对外定期发声的节奏。

具名致谢的门槛低，但被反复使用。Gleam 在 changelog 每一行后面括号署名；BAML 在发布文章里专门写一段致谢；[DSPy 路线图](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/roadmap.md) 列出完整贡献者名单。

中文语境下，公开反思设计判断这件事同样能带来正向互动——[LobeHub 那篇帖子](https://github.com/lobehub/lobehub/discussions/10007) 是证据。FastGPT、Dify 这类已经商业化的中文开发者工具，版本节奏比研究型语言项目快（FastGPT 近三个月平均约 3 天一个 Release，Dify 主仓库约 2–3 周一个正式版），这是产品成熟度和用户基数决定的结果，J++ 现阶段不需要模仿这个频率。

## 三、给 J++ 的建议

### 3.1 频率：新增一层双周摘要，不改动现有的逐项记录

`docs/progress.md` 和 `docs/updates/` 继续按现有约定走——每完成一项可验证进展就记一条，事件驱动，不设固定周期。

新增的是一层双周一次的对外摘要。理由：

- 项目五天内已有 16 篇内部更新，推进速度足够支撑周期性摘要；但仓库只有 9 颗星、1 个 issue，规模上比 marimo 开始月更时（3500+ Discord 成员）早得多。双周比每周更不容易出现「这两周其实没什么可写」的空转，也比每月更能让人感到项目在动。
- 双周节奏与「跑偏的识别」第一条呼应（`地基/00-定位与方法论-v1.md` 八·1）：如果连续两期摘要都写不出新的「已造出」条目，这本身就是一个需要停下来对照方法论的信号，摘要的周期性天然提供了这个检查点。

### 3.2 载体：先用 GitHub 原生工具，暂不新开需要长期维护的独立频道

第一个可以直接做的动作：开启 GitHub Discussions，建一个 Announcements 分类，双周摘要发在这里，README 顶部加一行链接。这比新开 Discord 服务器成本低（不需要设频道、定角色、配机器人），且和 GitHub Release、issue、PR 在同一个信任域里，读者不用跳转到另一个平台核实来源。

版本相关的内容继续走 `CHANGELOG.md` + GitHub Release（已有），双周摘要是这段时间内所有进展条目的人读版本，类似 This Week in Rust 把 Rust 项目各子系统一周内合并的 PR 重新组织成人读得下去的摘要。

中文层现在不开微信群：9 颗星、1 个 issue，群建起来大概率没人说话，之后要么荒废、要么需要额外精力维持话题，这个精力现在应该花在语言本身。等出现真实的中文开发者社区雏形（例如 Towow 生态里已经在用 J++ 写方法的人达到个位数以上、开始互相在 issue 里讨论）之后再开群，届时按用户给出的 OpenAgents 群模式执行：日常走用户案例、新集成、功能教程，频率 1–3 周一条；`@所有人` 只用于有实际行动要求、对所有人都相关、且资源有限的场合（例如试用名额、活动截止），日常功能更新不用。这个边界和英文项目的做法在结构上一致——This Week in Rust 把 Call for Participation 单独分节、和日常更新分开，本质上也是把「需要你现在做点什么」和「知道一下就行」区分开，只是英文项目没有 `@所有人` 机制，用分节代替。

在开群之前，可以先做成本更低的一步：把 README.zh-CN.md 和双周摘要保持同步更新，这是不开群也能维护的最小中文对外面。

### 3.3 每条通报的固定结构

参照 BAML/Outlines 的写法和 J++ 自己 `docs/maintaining.md` 已有的四项，双周摘要的每条条目固定五段，缺项就不写该段：

1. **改了什么**：一句话，写效果，不写实现细节（参照 `docs/progress.md` 现有写法）。
2. **怎么试**：可运行的命令或最小示例。
3. **谁做的**：具名，包括非代码贡献（文档、测试用例、issue 报告）。
4. **已知限制**（如果有）：参照 BAML「这不是吞吐量或端到端延迟基准」、Outlines「某功能已弃用且无替代」的写法，用范围描述写清楚这次进展没有覆盖到哪里。
5. **下一步**：写成别人可以认领的具体问题或任务。

### 3.4 研究期怎么征集用例

三件事，成本从低到高：

1. 每期摘要固定一个「Call for Participation」小节，参照 This Week in Rust 的格式：2–3 条具体的、边界清楚的任务，直接链接到 GitHub issue。这个小节的内容来自 `docs/maintaining.md` 里本来就要记录的「下一步或待解决的问题」，只是单独摘出来加一个可点击的入口。
2. 把 `CONTRIBUTING.md` 里已经写好的判据变成对外提问，每期问同一句话：「你有没有一个任务，手写判断逻辑要写很多行——试着用 J++ 写一遍，把写不出来的地方发给我们。」这句话对应 `地基/00-定位与方法论-v1.md` 的探针方法论（五·5.3）：不预设任务清单，邀请别人带真实任务来测语言的表达力。这是把内部已经在用的方法论，翻译成一句对外能听懂的邀请。
3. 给「带真实任务来试」的 issue 一个专门标签（例如 `probe` 或 `real-task`），呼应 [Modular](https://www.modular.com/blog/mojo-open-source) 用论坛把社区反馈汇总到一处的做法。这个标签同时也是未来回填「设计总账」（`地基/00-定位与方法论-v1.md` 术语表）的索引。

现在不设立正式的 alpha/beta 试用者计划——那需要专职团队维护社区论坛才撑得起，J++ 现在的规模用「标签 + Discussions 置顶帖」够用，等规模变化了再升级载体。
