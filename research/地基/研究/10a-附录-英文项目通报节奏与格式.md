J++ 社区通报调研：Gleam、Mojo/Modular、marimo、DSPy 四个项目的通报节奏与格式（均附一手来源，链接已于 2026-09-25 逐条检查返回 200）

正文写了四个项目：Gleam、Mojo/Modular、marimo、DSPy。BAML 的公开材料基本是自动生成的，写不出人工通报的节奏，文末单独说明；Outlines 只看了 release 列表。频率一律分成"项目自己怎么说"和"按日期实际算出来"两种，因为这两者普遍对不上。

来源可信度：GitHub Release、Mojo 发布说明源文件、Mojo 与 DSPy 的路线图源文件、Gleam CHANGELOG 都是用 gh/curl 直接读的原文。博客和 newsletter 的引文先由 WebFetch 摘要，其中关键句已用 curl 回原页面逐字核对（Gleam 6 句、marimo 6 句、Modular 博客 3 句，全部命中）。论坛帖子内容来自 Exa 抓取的全文。

本地查过 `地基/研究/README.md`，没有社区运营或通报相关的已有调研。

======================================================================
一、Gleam（社区驱动的语言，赞助者供养，1.0 前后都有记录）
======================================================================

【通报频率】
- 版本说明：每个 minor 版本都在 gleam.run/news 发一篇长文，通常与 GitHub tag 同一天。按 tag 日期算：1.0 之前 v0.25（2022-11-24）到 v0.34（2024-01-16）每 4–12 周一版；v1.0.0（2024-03-04）到 v1.18.0（2026-07-29）共 18 个 minor，平均约 7 周一版，范围 3.5–11.5 周。
- 预发布：每个 minor 先出 rc。例如 v1.18.0-rc1 在 7/21，rc2 在 7/25，正式版在 7/29；v1.16.0 出到了 rc4。
- 版本长文的标题按主题起，不写版本号，例如 "Upgrading Hex security" 就是 v1.15.0 的发布文。非版本新闻不定期，包括开发者调查（2022、2024）、路线图发布（2024-12）、GitHub Security Lab 协助（2026-08）、Gleam Gathering 大会等。
- Gleam Weekly 由社区自办，名义上是周刊。按 gleamweekly.com/issues 实际算，2025-08-28 到 2026-09-10 共 30 期，间隔 1–3 周；最近三期 #93 8/13、#94 8/27、#95 9/10 是双周一期。
来源：https://gleam.run/news/ ；https://github.com/gleam-lang/gleam/releases ；https://gleamweekly.com/issues

【载体及使用场合】
- GitHub Release 正文只有一行 CHANGELOG 链接，附带签名的构建产物（sha256、sigstore、SBOM），只负责分发。https://github.com/gleam-lang/gleam/releases/tag/v1.14.0
- CHANGELOG.md 是机器可查的权威记录。它按 rc 和正式版分节，节内分 Compiler、Build tool、Language server、Bug fixes 等，每条末尾用括号署名贡献者并链接其 GitHub。https://github.com/gleam-lang/gleam/blob/v1.14.0/CHANGELOG.md
- gleam.run/news 的长文是给人读的版本叙述。
- 路线图页 gleam.run/roadmap 分三块：In Progress（下个版本在做的，4 项）、Planned Features and Explorations（十余项，其中 4 项标 "Researching"）、Version History（v1.1 到 v1.18 每版做了什么）。未来项不写日期。https://gleam.run/roadmap/
- 社区渠道有 Discord、Bluesky、Reddit、Twitter/X 和 Gleam Weekly。官网社区页称后者为 "community-made Gleam Weekly newsletter"，页脚也放了链接。https://gleam.run/community/

【结构范例：v1.14.0 "The happy holidays 2025 release"】
1. 开头一句话介绍 Gleam 和本次版本："Gleam v1.14.0 is our Xmas gift for you, let's unwrap it and take a look inside."
2. 每个特性一节（本篇 21 节，另有收尾两节）：一段说明，一段代码示例（常带编译出的 Erlang/TS 代码），最后逐项致谢，例如 "Thank you Surya Rose and Yoshie for this!"
3. "And the rest" 节列出修 bug 的人："And thank you to the bug fixers and experience polishers: Adi Salimgereyev, Elias Haider, fruno, …"，并写明 "For full details … see the changelog"。
4. "A call for support" 节交代资金现状，后面先列公司赞助商 logo，再列全部个人赞助者姓名。
v1.14 和 v0.33 两篇长文都没有安装或试用步骤，v1.14 也没有"下一步"小节。1.0 前的 v0.33 在正文里顺带提过下一步："as we soon to hope to release a version 1.0.0"，以及浏览器 playground "which we hope to release in January"。
来源：https://gleam.run/news/the-happy-holidays-2025-release ；https://gleam.run/news/v0.33-exhaustive-gleam

【诚实度】
- 会承认已发布功能不完整。v0.33 写道："Unfortunately the implementation of exhaustiveness checking was, perhaps amusingly, inexhaustive. It did not work for more complex patterns."
- 会公开未达成的资金目标。v1.14 写道："Gleam is not owned by a corporation; instead it is entirely supported by sponsors … and Gleam is my sole source of income. We have made great progress towards our goal of being able to appropriately pay the core team members, but we still have further to go."
- 会公开不好看的调查结果。2022 年调查收到 211 份回复，结果文写 "It is disappointing that there are so few responses from women. This certainly is an area to improve on in future."，并提到多数受访者还没开始用 Gleam。
- 边界：路线图不写日期，所以不存在"延期"可以坦白；v1.14 长文里没有 known issues 节。
来源：同上，另有 https://gleam.run/news/developer-survey-2022-results

【早期（1.0 前）社区参与】
- v0.25 到 v0.34 每个版本都发了长文（见 gleam.run/news 列表），v0.33 文末致谢了全部贡献者和赞助者。
- 用开发者调查了解用户。2022 年问了背景、使用场景和信息来源，目的是弄清 "how to help people get started with Gleam and if there are any integrations we ought to build"。2024 年又做了一次：https://gleam.run/news/developer-survey-2024
- 赞助者名单本身就是致谢方式。v0.33 写道："I work full time on Gleam and your kind sponsorship is how I pay my bills!"，之后每篇都列出全部赞助者。
- 公开路线图到 1.0 之后（2024-12）才出。维护者写道 "I'll update it with each new Gleam release"，同时说明优先级由志愿者决定："it's up to individual contributors to decide what they find valuable and fun enough to work on." https://gleam.run/news/introducing-the-gleam-roadmap
- 没有找到 alpha/beta 试用者计划的公开证据，承担公测作用的是 rc 预发布。

二、Mojo / Modular（公司主导的语言，有"只能在托管 Playground 试用"的研究期）
======================================================================

【通报频率】
- 研究期（2022-09 到 2023-08）：每月一个发布说明文件，文件内按周或按日期分条。其中 2022-09 到 2023-04 这段不是当时公开发布的，而是内部周志在 2023-05-02 公布时一次性放出。Wayback 在公布当天抓到的 changelog 已经包含 "Week of 2022-09-26" 到 2023-04-24 的每周条目（http://web.archive.org/web/20230502175605/https://docs.modular.com/mojo/changelog.html ）。公开后的实时通报从 2023-05 开始。
  · 2022-09 文件只有 "Week of 2022-09-26" 一条，记的是第一个 lexer 补丁和"泛型用 [] 而不是 <>"这条设计决定。这说明研究期的通报也记录设计决定，不只记功能。https://mojolang.org/releases/2022-09/
  · 2023-05 文件有 05-02、05-11、05-16、05-24、05-31 五条，约每周一条。https://mojolang.org/releases/2023-05/
- 本地 SDK 发布后（2023-09 起）按版本发：v0.2.1（9/07）、v0.3.0（9/21）、v0.3.1（9/28）、v0.4.0（10/05）、v0.5.0（11/02）、v0.6.0（12/04）、v0.6.1（12/18）、v0.7.0（2024-01-25），2–5 周一版。https://github.com/modular/modular/blob/1b79ef249f52163b0bafbd10c1925bfc81ea1cb3/docs/changelog.md
- 近期：v0.25.6（2025-09-22）、v0.25.7（11-20）、v0.26.1（2026-01-29）、v0.26.2（03-19）、v1.0.0b1（05-07）、b2（06-18）、v1.0.0（08-11）、v1.1.0（09-17），5–8 周一版，另有 nightly changelog。https://mojolang.org/docs/changelog
- 社区会议自称 "a monthly gathering"，在 Zoom 上开，会后把录像放到 YouTube。第一次是 2024-05（Modverse #35："This week we held the first ever Mojo community meeting!"）。https://mojolang.org/community/ ；https://luma.com/sep-modular
- Modverse 通讯的频率一路下降。
  · #4（2023-10-10）自称 "This is our weekly high level summary"：http://web.archive.org/web/20251209015812/https://www.modular.com/modverse/modverse-weekly-4 （原址已 404）
  · #35 在 2024-05-23，仍约每周一期：http://web.archive.org/web/20250906013055/https://www.modular.com/modverse/modverse-weekly-35
  · 之后越来越稀：#50（2025-08-21）、#51（2025-09-19）、#52（2025-12-03）、#53（2026-03-06）、#54（2026-03-31）、又一期 #54（2026-05-04，编号重复）、#55（2026-06-10）。
  · https://www.modular.com/blog/modverse-50 ；https://www.modular.com/blog/modverse-54-from-gtc-to-edinburgh-a-community-building-momentum ；https://www.modular.com/blog/modverse-54-amd-ai-devday-new-modular-offices-and-a-community-that-keeps-shipping ；https://www.modular.com/blog/modverse-55-mojo-1-0-beta-community-mojo-libraries-and-real-time-patient-conversations-powered-by-max
- 论坛上的路线图更新不定期。已找到 2025-05-07（上半年路线图）、2025-07-14（Q3 更新附 Q2 回顾）、2025-08-26（愿景文档加新路线图）三次，不能据此说是"每季度一次"。

【载体及使用场合】
- 文档站的 changelog 是权威版本记录，每个版本一页，另有 nightly changelog，源文件放在 GitHub 仓库。
- 论坛 "Official Announcements" 用来发路线图更新和破坏性变更预警。https://forum.modular.com/t/mojo-q3-roadmap-update/1957
- 月度社区会议的议程在论坛预告，并收集提问，例如 "If you have any questions … please submit them here"。社区成员往议程文档里写上题目就能报名讲 10 分钟加 5 分钟问答，会后放出 YouTube 录像。https://forum.modular.com/t/february-community-meeting/2646
- Modverse 汇总社区项目和已合并的社区 PR，#51 写 "If you've recently had your first PR merged, message the Modular team in the forum to claim your epic Modular swag!"（https://www.modular.com/blog/modverse-51-modular-x-inworld-x-oracle-modular-meetup-recap-and-community-projects ）
- GitHub issues 收 bug，GitHub Discussions 收功能想法，Discord 用于日常交流。

【结构范例】
(a) 研究期（2023-05）：用 emoji 分节 📢 Released / ⭐️ New / 🦋 Changed / 🛠️ Fixed。New 下第一条是 "Mojo Playground now includes the following Python packages (in response to [popular demand](…/discussions/173))"，直接回应了社区讨论帖；Fixed 条目引用 "Issue #18" 这类编号。
(b) 1.x（v1.1.0）：依次是 Highlights（粗体标题加一两句说明，链接到详细小节）、Documentation、Language enhancements、Language changes、Library stabilizations、Library performance improvements、Library changes（按领域分子节）、GPU programming、Tooling changes、Removed（按类别列出被删的 API）、Fixed（按领域分组并引用 issue），最后是 Special thanks："Special thanks to our community contributors: Amr Hesham (@AmrDeveloper), …"。https://mojolang.org/releases/v1.1.0/
(c) 论坛路线图更新（2025-07-14）：先回顾上季度做完了什么（Q2 (April-June) Recap），再列本季度优先级，每项写 "Why?" 和 "How?"。开头一段就请读者 "Please post any questions and feedback in this thread!"。
(d) 早期 changelog 里有 "### Known Issue" 小节，例如 v0.6.0："There is an issue affecting Jupyter notebooks that use autotuning and traits. This issue only manifests on macOS … affects the Matrix multiplication in Mojo notebook."

【诚实度】（四个项目里最系统）
- 2023–2024 年的路线图页标题就叫 "Mojo🔥 roadmap & sharp edges"，页内有两节。
  · "Mojo SDK known issues" 逐条列出已知问题、绕过办法和对应 issue 链接。
  · "Sharp Edges" 开头写："Given that Mojo is still a young language, there are a litany of missing small features … as well as features that don't quite work the way we want to yet … We expect all of these to be resolved in time, but in the meantime, they are documented here."
  · 它还明确写了近期不做什么："In the near-term, we will not prioritize 'general goodness' work such as: Adding syntactic sugar …"
  · 以上三处引文都出自 2024-03 的快照：https://github.com/modular/modular/blob/1b79ef249f52163b0bafbd10c1925bfc81ea1cb3/docs/roadmap.md
  · 2023-06 的存档里已经有 "Sharp Edges" 节（含 "litany of missing small features" 一句）和 "general goodness" 不优先清单，但没有 "Mojo SDK known issues" 节。SDK 在 2023-09 才发布，这一节是之后加的。存档：http://web.archive.org/web/20230611215921/https://docs.modular.com/mojo/roadmap.html
- 现行路线图用 ⬜/🚧/✅ 标状态，并写明 "this isn't an exhaustive list of work, and the status might be out of date"，各阶段 "have no timeline for completion"。https://mojolang.org/docs/roadmap/
- 破坏性变更会提前预警并道歉（2026-07-21）："These module moves unfortunately may break some of your Mojo code … Apologies for the dust"。https://forum.modular.com/t/mojo-standard-library-reorganization/3337
- 会承认生态问题。Q3 更新写道："Many community packages are not compatible with the latest nightly builds, and in some cases, even the latest stable release."
- 会承认团队精力有限。Chris Lattner 在讨论并发支持时说："the Mojo core team hasn't had head space to properly evaluate any particular approach yet." https://forum.modular.com/t/concurrency-support/1616

【早期（研究期）社区参与】
- 语言公布前先做用户调研。2022-12 的帖子写 "We want to hear what pain points you are experiencing …"，填问卷的回报是 "early access to our platform when it's ready"。https://www.modular.com/blog/we-want-to-hear-from-you
- 研究期只开放托管环境："Mojo 🔥 is still in development but it's available to try today with our JupyterHub-based Mojo Playground"（2023-05-02）。四个月后公布的数字是："more than 120K+ developers have signed up to use the Mojo Playground and 19K+ developers actively discuss Mojo on Discord and GitHub"（2023-09-07）。https://www.modular.com/blog/a-unified-extensible-platform-to-superpower-your-ai ；https://www.modular.com/blog/mojo-its-finally-here
- 分流反馈渠道：bug 走 GitHub issues，想法先在 GitHub Discussions 讨论（见路线图原文），与 Python 通用改进相关的建议引导走 PEP 流程。
- 社区成员可以在月度会议上讲自己的项目。首个 PR 被合并的人可以领周边。近期版本（如 v0.26.2、v1.1.0）的发布说明末尾都列出社区贡献者名单。

三、marimo（Python 笔记本，发版最频繁，newsletter 做得最完整）
======================================================================

【通报频率】
- GitHub Release：2025-03-27 到 2026-09-23 共 100 个，发版间隔中位数 4 天，以 patch 为主。只有 minor 版本（如 0.24.0 在 8/17、0.25.0 在 9/23）才写长篇 Highlights。https://github.com/marimo-team/marimo/releases
- Newsletter 自称 "This is your monthly reminder …"（#19–#22 都这样写）。按日期实际算：#19（2025-10-30）、#20（11-20）、#21（2026-01-12）、#22（02-12）、#23（04-07）、#24（05-01）、#25（06-01）、#26（07-27），间隔 3–8 周。2025 年 12 月和 2026 年 3 月没有出刊，6/1 到 7/27 之间隔了 8 周。从 #1（2024-02-13）到 #26 平均约 5 周一期。
- 其他：大版本单独写博文（如 marimo-0-19-0），2026-07 办了第一次 launch week（连续 5 天、每天发一项），另有社区电话会和笔记本竞赛。https://marimo.io/blog/launch-week-1

【载体及使用场合】
- GitHub Release 是版本说明的主载体，上半部分人写，下半部分自动生成的 PR 列表。
- Newsletter 同时发邮件和博客（/blog/newsletter-N），做月度汇总。
- 博客发路线图、launch week 和案例研究。
- 社区渠道有 Discord（#26 称已 4k+ 人）、Reddit、X、Bluesky、LinkedIn、YouTube。

【结构范例 1：Release 0.25.0】
1. 开头一段交代本版主题，接一句加粗的升级判断："We expect most users to be able to upgrade without making changes."，并说明哪些工作流可能受影响。
2. ⭐️ Highlights：每个特性说明做了什么，给出能直接复制的试用命令（如 `uvx marimo edit --sandbox notebook.py`，或 `pixi exec marimo edit --sandbox=pixi notebook.py`），再链接到指南。会注明来由（"One of our most-requested features is here"），也会点名（"This was also one of the first contributions from our newest team member, @marthacryan!"）。
3. 之后依次是 ✨ Enhancements、🐛 Bug fixes、📚 Documentation、🔬 Preview features、📝 Other changes，每条都链接 PR。有破坏性变更的版本另加 "🚨 Breaking changes" 节。
4. Contributors 节写 "Thanks to all our community and contributors who made this release possible: @akshayka, @atul2387, …"。
5. New Contributors 节逐条写 "@X made their first contribution in #PR"。
6. 最后是 Full Changelog 的 compare 链接。
来源：https://github.com/marimo-team/marimo/releases/tag/0.25.0

【结构范例 2：Newsletter #26】
依次是：Launch week 回顾 → What's new on molab → 客户案例 → New features in marimo open source（汇总 0.23.9 到 0.23.15 七个版本）→ Trending on YouTube → 笔记本竞赛结果 → Community roundup（固定报一行社区数字："We're at 22k+ GitHub stars, 300+ contributors, … and 4k+ members in Discord"）→ 一张趣味图。好几期还附了问卷，例如 #21 的 "please give us feedback by taking our two-minute survey"。
来源：https://marimo.io/blog/newsletter-26 ；https://marimo.io/blog/newsletter-21

【诚实度】
- Release 层比较坦白：经常有 "🚨 Breaking changes" 节，回滚的提交照常列出，0.13.12 直接标注 "[This release was yanked due to GitHub Copilot issues]"。https://github.com/marimo-team/marimo/releases/tag/0.13.12
- Newsletter 层只报喜。深读的 #26 没有提任何问题或延期，其余几期只看了摘要。
- v1 路线图（2025-01-06）列了六个目标，不写日期，也不标哪些不确定。https://marimo.io/blog/v1-roadmap

【早期社区参与】
- 公开发布前做过 beta。2024-02-05 的发布文写道："With feedback from beta users in research institutions and tech companies, I worked for over a year to build marimo." 以及 "We're a team of just two developers, and we're just getting started."。不过 GitHub 仓库和 0.1.0 在 2023-08-14 就公开了，beta 期与公开发版有重叠。没有找到 beta 用户是怎么招募的公开说明。https://marimo.io/blog/introducing-marimo
- Newsletter #1 请读者直接回信："just reply to this email to start a conversation"。https://marimo.io/blog/newsletter-1
- 路线图请读者到 GitHub discussion 反馈："Have feedback on our roadmap? Join our GitHub discussion"。
- 后期用问卷、竞赛（奖品是 Mac Mini）、launch week 猜题送周边、社区电话会来维持参与。

四、DSPy（斯坦福研究项目演化成的框架，论文驱动）
======================================================================

【通报频率】
- GitHub Release：2024-09-28 到 2026-09-11 共 100 个，中位间隔 2 天，主要是 2025 年 2.6.x 的密集 patch。近期 minor 版本 3.1.0（2026-01-06）、3.2.0（04-21）、3.3.0（08-03）、3.4.0b1（09-11）约 3–4 个月一个，正式版之前先出 beta。
- 没有找到官方博客或 newsletter。README 让读者关注 "@DSPyOSS on Twitter or the DSPy page on LinkedIn"，另有 Discord。https://github.com/stanfordnlp/dspy/blob/main/README.md
- 研究期（2023 年）的发布靠作者的 Twitter 线程和 arXiv 论文。README 列了 "Introducing DSP"（2023-01）、"Releasing the DSP Compiler (v0.1)"（2023-02）、"Releasing DSPy, the latest iteration of the framework"（2023-08）三条线程。线程原文需要登录 X 才能看，这里只引用 README 里的列表。

【发布说明的演变】
大版本一直是人写的。3.0.0（2025-08-12）已经有 "✨ Highlights across 2.6 → 3.0"、"💥 Breaking changes / notable removals"、"🆚 Changes since 3.0.0b4"、"👏 Contributors since 2.6" 等节。2.6.x 这类 patch 和 3.1.0 用的是 GitHub 自动生成的 "What's Changed" PR 列表。从 3.2.0（2026-04-21）起，minor 版本固定写人写的 Highlights，每节标题后面带作者 handle。https://github.com/stanfordnlp/dspy/releases/tag/3.0.0

【结构范例：3.3.0 与 3.4.0b1】
1. 一段总述。
2. 兼容性判断："Most existing DSPy programs should keep working without changes. Review the API changes if you …"，后面列出受影响的具体用法。
3. 点名要哪些反馈："We would especially appreciate feedback on Flex, ReActV2, and the typed LM path … real-world usage will help shape their next iterations."
4. Highlights：每节标题形如 "### Flex Optimizes Program Structure, Not Just Prompts — @michaelisaac-dev"，内容是说明、代码示例、"experimental" 标注和 "PR: #10047"。有实测数字时会注明条件，例如 "We have seen up to 50% decreases in cost for some tasks when testing this internally."
5. API Changes 下分三块：Breaking Changes（每项附 Before 和 After 代码）、New and Updated APIs、Compatibility Notices。
6. Full PR List 按领域分组，并标明每组 PR 数（如 "Agents, Tools, and Interpreters — 25 PRs"）。
7. Contributors 节写 "Thank you to everyone who contributed to DSPy 3.3.0:"，列出 handle，并注明 "Automation contributions were made by @dependabot and @github-actions."。
8. First-Time Contributors 节逐条写 "@X made their first contribution in #PR"。
beta 版额外有三样东西。一是加粗声明："This is a prerelease, not the stable 3.4.0 release. APIs and behavior may change before stable."。二是明确要什么反馈："We especially welcome feedback on native versus LiteLLM compatibility, tool calling and streaming, … Please include your engine selection and a minimal reproduction when reporting issues."。三是给出安装命令 `pip install --upgrade "dspy==3.4.0b1"`，并写明迁移时间线："3.4 is the LM transition release; 3.5 is the migration deadline."。
beta 转正式的说法（3.0.4）："3.0.4b2 has been running for a while without seeing issue, so we are making it an official 3.0.4 release."

【诚实度】
- 2024-08 的路线图对不足写得很直白。
  · "most DSPy users in practice explore prompt optimization and not weight optimization … The primary reason for a lot of this is infrastructure."
  · "Using DSPy well for solving a new task is just doing good machine learning with LMs, but teaching this is hard."
  · 代码里有一部分 "exist only because the LM space lacks the building blocks we need"，因此预计 "reduce around 6000 LoCs … by shifting a lot of that to LiteLLM"。
  · "While we cannot share the internal details of research on new optimizers yet, we can outline the goals."

- Release 层会标 experimental 和 beta，破坏性变更附迁移代码。

======================================================================
六、跨项目观察（供写正式文档参考）
======================================================================
1. 通报普遍分三层。机器层是 nightly、rc 和 CHANGELOG，自动生成、密度高。版本层是每个版本一份人写的说明。叙事层是 newsletter、社区会议和路线图更新，面向不写代码的关注者，频率最低。Gleam 把后两层合并成一篇长文；marimo 和 Modular 三层分开做。
2. 自称的频率普遍高于实际。Gleam Weekly 名为周刊，实际 1–3 周一期；Modverse 自称周刊，后来掉到 1–3 个月一期，还出现了编号重复；marimo 说 "monthly"，实际有跳月。所以对外承诺的节奏应取团队能长期守住的下限。
3. 研究期可以借鉴 Mojo 的做法：每周一条带日期的变更记录，把设计决定也写进去。Mojo 在未公开的 7 个月里一直在内部写周志，公布那天把整段历史一起放出；路线图直接放 known issues 和 sharp edges，写明近期不做什么；试用先限定在托管环境里，用问卷换早期访问资格。
4. 致谢形式有三种：逐条署名（Gleam 的 changelog、DSPy 的 Highlights 标题、Mojo 的 Special thanks），文末名单，首次贡献者单列（marimo、DSPy）。Gleam 还把赞助者全名单写进每篇长文。
5. 征求反馈时写得越具体越有用。DSPy 的 beta 说明点名了要哪五方面的反馈，并要求附最小复现和引擎选择；Mojo 在发布说明里直接链接到提出需求的 Discussion #173；marimo 用加粗的一句话告诉用户能不能放心升级。
6. 各层的诚实程度不同。版本层普遍坦白，会写 breaking changes、yanked、known issue 和回滚。叙事层（newsletter）基本只报喜。四个项目里都没找到"某个数字没达标"或"某件事延期"的明确公告。最接近的例子是：Gleam 公开资金目标还没达到、公开调查结果令人失望；DSPy 承认多数用户不用权重优化；Mojo 承认社区包兼容性差、团队没有精力评估并发方案。原因之一是它们的路线图都不写日期，也就没有"延期"可以承认。J++ 如果想比这些项目更诚实，可以在固定位置写"本期未达标/延期"一栏，在本次查看的材料中没有见到这种做法。
