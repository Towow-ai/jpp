## English

J++'s design intent is that JEV (the cheap judgment primitive), a generator, an executor, and exact algorithms are meant to compose -- not just be callable, but usable as elements inside larger constructed programs (`地基/00-Nature意图汇编.md` §2). Up to now the host side of that -- the concrete actions a `.jpp` program's `do` can call -- had three actions total: `record_check`, `read_json`, `write_json`. This block adds eleven more, split across two kinds.

**One table, not three places that can drift.** Before this block, a CLI action's facts (its name, whether it's reversible, its output trust tag, its cost, the code that runs it) were written in three separate places: a registration table, a per-action closure, and a hand-written sentence in the `--help` text. Two steps collapsed this to a single source: `crates/jpp/src/actions/` now holds one table (`BUILTIN_ACTIONS`) that both `check` (for its static J-08/J-11 diagnostics) and `run` read from, and it lives in the library target rather than the CLI binary, so anything linking against the `jpp` crate sees the same table the CLI does. Adding a new action means adding one row.

**Six exact-algorithm actions (`graph:matching`, `graph:shortest_path`, `graph:max_clique`, `graph:components`, `graph:set_cover`, `graph:max_flow`).** Each takes a JSON edge/node list and returns a JSON result that includes the input edge indices it used, so a program built with `judged_graph`/`on_graph` composition primitives can trace which judged edges a graph algorithm's output depended on. All six were checked against an independent brute-force implementation on 200 randomly generated graphs each, with zero mismatches, and timed on realistic sizes: a 325-node bipartite matching in 21.5ms, a 325-node shortest path in 5.3ms, a 325-node max-flow in 11.1ms, 325-node connected components in 4.2ms. Two algorithms don't scale to 325 nodes by design, not by oversight: maximum clique is NP-hard, so it's timed at its documented exact-solution limit of 60 nodes instead (0.49ms there); general (non-bipartite) weighted matching uses an exact bitmask search capped at 20 nodes, with bipartite matching (which does reach 325 nodes) handled by a separate Kuhn-Munkres implementation.

**Five executor and retrieval actions (`exec_py`, `check_tests`, `exec_sql`, `embed_topk`, `bm25_topk`).** `exec_py` runs arbitrary Python code in a subprocess; `check_tests` reuses the same machinery to run a code snippet against a set of assertions; `exec_sql` runs a single SQL statement against a SQLite database. `embed_topk` and `bm25_topk` both rank a list of texts against a query and return `[{id, score}]`: the first calls a local MiniLM sentence-embedding model through a subprocess (interpreter path configurable via `JPP_EMBED_PYTHON`, no path is hard-coded into the binary -- an earlier version of this action did hard-code a path to a specific development machine's Python virtual environment, caught and corrected in review before merge), caching corpus embeddings by content hash so repeated queries against the same corpus skip re-embedding it; the second is a dependency-free Rust implementation of BM25 ranking with simple CJK single-character tokenization.

**What actually isolates the three code-running actions, stated plainly.** An initial version of `exec_py`/`check_tests` relied on a static scan of the code text (rejecting `import os`/`subprocess`/`socket`/`shutil`, `eval`/`exec`/`compile`/`__import__`, write-mode `open()` calls) plus a runtime patch on `socket.socket.connect`/`getaddrinfo` -- and marked both actions `reversible: true` on that basis. PR review (both an external reviewer and the coordinating session's own testing) found this insufficient: a static text scan cannot catch every way to write a file (`pathlib.Path(...).write_text(...)` matches none of the listed keywords), so `reversible: true` was not a safe claim. The actions now additionally run inside an OS-level sandbox -- macOS `sandbox-exec`, Linux `bwrap` -- which is the layer that actually enforces the isolation; the static reject list and network patch remain as a second, defense-in-depth layer, not the primary mechanism. **What the sandbox blocks:** writing anywhere outside a fresh per-call temporary directory; opening a network connection. **What it does not block, stated in the module's own header comment rather than left implicit:** reading any file the host process can read; CPU, memory or process-count limits (no fork-bomb protection). The host probes for a working sandbox tool once at startup -- not by checking whether the binary merely exists, but by actually running a minimal command through it and checking the exit code, since a CI runner can have `bwrap` installed yet unable to use it (restricted, unprivileged user namespaces are common in containerized CI images) -- and caches the result for the process's lifetime. When no usable sandbox is found, the three actions are marked non-reversible and `check`/`run` now fail at the static-check stage with a new diagnostic, `E-action-no-sandbox`, unconditionally -- whether or not the call site has a guard, because an unavailable sandbox is an environment problem, not a permission problem a guard can address. Integration tests that need a real sandbox to exercise this path call the same probing function the production code uses and print a reason and skip, rather than fail, when it comes back unavailable -- so this sync's public CI (a Linux runner with no `bwrap`) is expected to skip these specific cases rather than fail on them, and the tests that exercise the *no-sandbox* rejection path itself are unaffected either way.

**A fourth defense layer for `exec_sql`, closing a gap the read-only connection alone did not cover.** The coordinating session's own testing found that `exec_sql`'s `mode=ro` read-only connection open does not stop `VACUUM INTO` or `ATTACH DATABASE`, both of which can create new files on disk without writing to the already-open database file the read-only flag protects -- a more severe finding than the four issues raised in review. The fix adds `PRAGMA query_only` plus a SQLite authorizer callback that allow-lists only `SELECT`/`READ`/`FUNCTION`/`RECURSIVE` actions and denies everything else; a denied statement now fails the call outright (`Fail`) rather than being reported through the same structured `error` field used for ordinary content errors like a syntax mistake, keeping a security-boundary rejection distinguishable from a query that was merely wrong. This stacks with the OS sandbox described above as a fourth, independent layer.

**Two more review fixes, smaller in scope.** A `truncate` helper used to shorten long subprocess output could panic if the cut point landed inside a multi-byte UTF-8 character; it now backs off to the nearest character boundary. Several of the graph actions used a fixed absolute floating-point threshold (`1e-9`/`1e-12`) to treat near-zero values as exactly zero, which silently dropped real, valid edges or capacities smaller than that threshold while still reporting `"exact": true`; `max_flow` now scales its threshold to the input's own magnitude instead of using a fixed cutoff, and the exact-DP paths for matching, shortest-path and set-cover -- which do not need a tolerance for floating-point noise in the first place -- now compare values exactly instead.

**A design-text gap, filled rather than silently expanded around.** The task instructions for this block listed four executor/retrieval actions; the design texts (`12-IR与类契约-v0.1.md` ruling B150, `21-工程方案-v1.md` step 24e-1) list `exec_sql` in the same group. Rather than either skip it silently or add it without checking, the implementing agent flagged the mismatch, confirmed with the coordinating session that it was a real omission rather than an intentionally deferred item, and added it in a small follow-up.

**Verification.** All four blocks' own test suites passed at merge time (matching-and-shortest-path pair, then the remaining four graph algorithms, 200-case brute-force comparisons for each; the executor/retrieval actions, 29 module-level tests plus 8 CLI integration tests covering first-run behavior and ledger-only replay with zero calls). This sync's own from-scratch verification against the merged state: `cargo fmt --check`, `cargo clippy --workspace --all-targets --keep-going` (73 warnings, matching this repository's recorded baseline, no new warnings anywhere in this block), and `cargo test --locked --workspace` -- see [progress.md](../progress.md) for the combined pass count across this whole sync.

**Verification, security-hardening round.** Applied on top of the above, on this same PR, after review. `cargo build --locked --workspace` and `cargo fmt --check` are clean; `cargo clippy --workspace --all-targets --keep-going` reports 72 warnings (down from 73, no new warnings from anything touched here). The affected and neighboring test files (`actions_exec_py`, `actions_check_tests`, `actions_exec_sql`, `actions_graph`, `actions_bm25_topk`, `actions_embed_topk`, the new `actions_no_sandbox`, `b116_questions_out`, `golden`, `diag_json`, `bypass_j08_check_actions`, `bypass_j11_unregistered_action`, plus the `jpp` crate's lib and bin unit tests) all pass on this machine (macOS, where `sandbox-exec` is genuinely available, so the sandboxed paths run for real rather than skip); a full-workspace rerun was not repeated a second time for this incremental change, per this project's practice of running the full suite once per completed step and relying on targeted reruns in between.

## 中文

J++ 的设计意图是让 JEV（便宜的判断原语）、生成器、执行器与精确算法能够搭配——不只是能被调用，而是能作为元素嵌进更大的构造程序里（`地基/00-Nature意图汇编.md` §二）。到目前为止，这件事在宿主一侧的落地——`.jpp` 程序的 `do` 能调用哪些具体动作——总共只有三个：`record_check`、`read_json`、`write_json`。这一批施工加了十一个新动作，分两类。

**一张表，不再是三处容易漂移的地方。** 这批施工之前，一个 CLI 动作的事实（名字、是否可逆、输出可信标签、成本、执行代码）分写在三处：注册表、各动作自己的闭包、`--help` 文本里手写的一句话。两步把这些收成单一来源：`crates/jpp/src/actions/` 现在有一张表（`BUILTIN_ACTIONS`），`check`（用于它的 J-08/J-11 静态诊断）与 `run` 都从这里读，而且它放在库目标而不是 CLI 二进制里，所以任何链接 `jpp` crate 的代码都能看到 CLI 看到的同一张表。加一个新动作，就是加一行。

**六个精确算法动作（`graph:matching`、`graph:shortest_path`、`graph:max_clique`、`graph:components`、`graph:set_cover`、`graph:max_flow`）。** 每个都接收 JSON 边/节点列表，返回的 JSON 结果带上它用到的输入边下标，这样一个用 `judged_graph`/`on_graph` 组合原语搭出来的程序，能追溯图算法的产物依赖了哪些经过判断的边。六个都对独立的暴力实现跑过各 200 组随机图对拍，零分歧，并在真实规模上计过时：325 节点二分图匹配 21.5 毫秒、325 节点最短路 5.3 毫秒、325 节点最大流 11.1 毫秒、325 节点连通分量 4.2 毫秒。两个算法没有跑到 325 节点，是设计决定不是疏漏：最大团是 NP-hard，按它文档明写的精确解上限（60 节点）计时（0.49 毫秒）；一般图（非二分）带权匹配用精确位掩码搜索、上限 20 节点，能跑到 325 节点的是二分图匹配，用的是另一套 Kuhn-Munkres 实现。

**五个执行器与检索动作（`exec_py`、`check_tests`、`exec_sql`、`embed_topk`、`bm25_topk`）。** `exec_py` 在子进程里跑任意 Python 代码；`check_tests` 复用同一套机制，让一段代码对一组断言跑一遍；`exec_sql` 对一个 SQLite 数据库跑一条 SQL 语句。`embed_topk` 与 `bm25_topk` 都是拿一批文本对一个查询排序，返回 `[{id, score}]`：前者经子进程调本地 MiniLM 句向量模型（解释器路径可配置，`JPP_EMBED_PYTHON`，二进制里不写死路径——这个动作的早期版本确实写死过一台开发机的 Python 虚拟环境路径，合入前复核时被发现并改正），按内容哈希缓存语料向量，同一语料的重复查询不用重新编码；后者是不依赖新库的纯 Rust BM25 实现，CJK 按单字做简化分词。

**三个跑代码的动作到底靠什么隔离，如实写。** 早期版本的 `exec_py`/`check_tests` 只靠扫代码文本的静态拒绝表（挡 `import os`/`subprocess`/`socket`/`shutil`、`eval`/`exec`/`compile`/`__import__`、写模式的 `open()`）加一层运行期给 `socket.socket.connect`/`getaddrinfo` 打的补丁，并在这个基础上把两个动作标成 `reversible: true`。PR 评审（一名外部评审与协调会话自己的实测）指出这不够：静态文本扫描挡不住所有写文件的写法（`pathlib.Path(...).write_text(...)` 不含任何一条拒绝表关键字），`reversible: true` 因此不是一个安全的断言。现在这三个动作额外跑在操作系统级沙箱里——macOS 用 `sandbox-exec`、Linux 用 `bwrap`——这才是真正起隔离作用的那一层；静态拒绝表与网络补丁仍然保留，作为第二层纵深防御，不是主防线。**沙箱挡得住什么：** 往每次调用新建的临时目录以外的任何地方写文件；发起网络连接。**挡不住什么，写在模块自己的头注释里、不是留给读者猜：** 读宿主进程能读到的任意文件；不限制 CPU、内存、进程数（不防 fork 炸弹）。宿主启动时探测一次沙箱工具是否可用——不是只看这个二进制存不存在，而是真的用它跑一次最小命令、核对退出码——因为 CI 跑的机器可能装了 `bwrap` 却用不了它（容器化 CI 镜像常见的非特权用户命名空间限制），探测结果缓存整个进程生命周期。探测不到能用的沙箱时，这三个动作被标为不可逆，`check`/`run` 现在会在静态检查阶段就报一条新诊断 `E-action-no-sandbox`——不管调用点有没有守卫都报，因为沙箱不可用是环境问题，不是守卫能解决的权限问题。需要真沙箱才能跑的集成测试调用与生产代码同一个探测函数，探测不到就打印原因跳过而不是判失败——所以这次同步的公开仓库 CI（没有 `bwrap` 的 Linux runner）预期会跳过这几条具体用例而不是报错，测「没有沙箱本身该被拒绝」这条路径的测试则不受影响，照常跑通。

**给 `exec_sql` 加的第四层防线，补上只读连接本身没挡住的口子。** 协调会话自己实测发现，`exec_sql` 的 `mode=ro` 只读连接挡不住 `VACUUM INTO` 或 `ATTACH DATABASE`——这两条语句能在磁盘上新建文件，不需要写入只读位保护的那个已打开的数据库文件本身，这条发现比评审提出的四条更严重。修法是加 `PRAGMA query_only` 加一个 SQLite 授权回调，只放行 `SELECT`/`READ`/`FUNCTION`/`RECURSIVE`，其余一律拒绝；被拒绝的语句现在直接让调用失败（`Fail`），不再经过普通内容性错误（比如语法写错）共用的那个 `error` 字段——让「触碰了安全边界」和「问题写错了」两种失败能分得开。这一层与前面的操作系统沙箱叠加，是第四道独立防线。

**另外两处规模较小的评审修复。** 一个用来截断过长子进程输出的 `truncate` 函数，如果截断点正好落在一个多字节 UTF-8 字符中间会 panic；现在会退到最近的字符边界。几个图算法动作原先用固定的绝对浮点阈值（`1e-9`/`1e-12`）把接近零的值当成恰好是零，这会悄悄丢掉真实存在、只是数值小于这个阈值的边或容量，却仍然报 `"exact": true`；`max_flow` 现在按输入自身的量纲取相对阈值而不是写死一个界，`matching`、`shortest_path`、`set_cover` 的精确 DP 路径——这几条本来就不需要容忍浮点噪声——现在直接比较精确相等。

**设计文本的一处缺口，补上而不是悄悄绕开。** 这一批任务指令列出的执行器/检索动作是四个；设计文本（`12-IR与类契约-v0.1.md` B150 裁定、`21-工程方案-v1.md` 步 24e-1）把 `exec_sql` 列在同一组里。施工代理没有悄悄跳过或径自加上，而是指出了这处不一致，向协调会话核实确认这是一处真实遗漏、不是有意留待后续的项目，再在一次小的后续提交里补上。

**验证。** 四块施工各自的测试套件在合入时都已通过（matching 与 shortest_path 一对，随后其余四个图算法，各自 200 组暴力对拍；执行器/检索动作 29 条模块级测试加 8 条 CLI 集成测试，覆盖首跑行为与只凭账本重放零调用）。本次同步对合入后的状态又做了一遍从零验证：`cargo fmt --check`、`cargo clippy --workspace --all-targets --keep-going`（73 条告警，与本仓库记录的基线相同，这一批里没有任何新增告警），以及 `cargo test --locked --workspace`——本次同步整体的合计通过数见 [progress.md](../progress.md)。

**验证，安全加固这一轮。** 在评审之后、同一个 PR 上叠加。`cargo build --locked --workspace` 与 `cargo fmt --check` 干净；`cargo clippy --workspace --all-targets --keep-going` 报 72 条告警（比之前的 73 少，这一批没有任何新增）。受影响与相邻的测试文件（`actions_exec_py`、`actions_check_tests`、`actions_exec_sql`、`actions_graph`、`actions_bm25_topk`、`actions_embed_topk`、新增的 `actions_no_sandbox`、`b116_questions_out`、`golden`、`diag_json`、`bypass_j08_check_actions`、`bypass_j11_unregistered_action`，加上 `jpp` crate 的 lib 与 bin 单元测试）在本机（macOS，真的有 `sandbox-exec`，所以走沙箱的路径是真跑而不是跳过）全部通过；这次增量改动没有再跑一遍全量测试，遵循本项目「每完成一步跑一次全量、期间用相关测试」的惯例。
